# local-rag-agent

Локальный агент для вопросов на естественном языке по личному архиву исследовательских файлов: код Python (`.py`), Jupyter-ноутбуки (`.ipynb`), PDF, изображения (`.png`), DOCX и TXT. Ответы по файлам содержат ссылки на источник: файл и строки, ячейку ноутбука, страницу. На общие вопросы (теория, код с нуля, разговор) агент отвечает из знаний модели и помечает это. Всё работает на локальной машине. Данные корпуса, индексы и трассы в сеть не уходят.

Сейчас индексируются `.py`, `.ipynb`, `.pdf` (включая сканы через OCR), `.docx`, `.txt`, `.md`, `.log`. `.doc` индексируется, если установлен LibreOffice. Изображения `.png` — этап Э5. Подробности — в разделе «Статус» ниже.

Обоснование проекта — [анализ литературы и техническое задание](docs/TZ.md): обзор работ по обеим частям ТЗ, из выводов которого сформированы проблемы, решения, гипотезы, требования и этапы; ссылки вида [n] ведут в общий список литературы в конце документа.

## Статус

Проект идёт по двум частям технического задания:

- **Часть 1** (Э1–Э10) — вопросно-ответная система с цитированием над корпусом `.py`, `.ipynb`, `.pdf`, `.png`.
- **Часть 2** (Э11–Э17) превращает её в рабочего ассистента. Добавляются:
  - форматы DOCX и TXT;
  - режим рассуждений;
  - загрузка файлов;
  - код-агент в изолированной песочнице;
  - поиск в интернете.

  Все действия агента в Части 2 проходят через слой политик доступа. Он нужен, чтобы приватные данные не утекли через инъекции в промпт.

**Отступления от ТЗ, известные заранее:**

- **Песочница.** gVisor и Firecracker работают только в Linux. На Windows код будет исполняться в контейнере Docker Desktop, внутри виртуальной машины WSL2:
  - без сети;
  - корпус подключён только на чтение;
  - процесс без прав root;
  - лимиты ресурсов;
  - новый контейнер на каждую задачу.

  gVisor остаётся вариантом для Linux и WSL2.
- **Сеть в песочнице (NFR8).** По умолчанию сети нет. По желанию пользователя её можно разрешить переключателем «Сеть для кода» — для скачивания данных и установки пакетов. Каждая задача с сетью требует отдельного подтверждения (правило «сначала план, потом исполнение», FR17). `code.network: never` возвращает строгий вариант ТЗ.
- **Модель для кода.** Для кода, кроме основной модели, рассматривается специализированная кодовая модель. ТЗ это допускает.

## Требования

- Python 3.11+ и PyTorch. Подходит сборка под ROCm (AMD), CUDA (NVIDIA) или CPU. Проверено на RX 7900 XTX: Windows 11, ROCm 7.2, torch 2.9.
- [Ollama](https://ollama.com) и LLM, по умолчанию `qwen3.5:9b`:
  ```bash
  ollama pull qwen3.5:9b
  ```
- Эмбеддер [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3), около 2.3 ГБ, скачивается с Hugging Face:
  ```bash
  hf download BAAI/bge-m3 --exclude "onnx/*"
  ```
- Реранкер [BAAI/bge-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3):
  ```bash
  hf download BAAI/bge-reranker-v2-m3
  ```
- Модели Docling для PDF: вёрстка, таблицы, OCR для русского и английского.
  ```bash
  docling-tools models download layout tableformer easyocr --easyocr-lang ru --easyocr-lang en
  ```
- Для оценки: модель-судья, по умолчанию `qwen3.6:27b`:
  ```bash
  ollama pull qwen3.6:27b
  ```

Все модели загружаются только из локального кэша (`embedding.local_files_only`). Во время работы система ничего не скачивает. Если модели нет, ошибка подскажет команду для загрузки.

> **Встроенная графика AMD и Ollama.** Если у процессора есть встроенная графика (например, Ryzen 7000), Ollama может запустить модель на ней, когда дискретная карта занята другой моделью. Запуск тогда падает с ошибкой `ROCm error: device kernel image is invalid`. Чтобы этого не было, ограничьте Ollama дискретной картой и перезапустите Ollama:
> ```bash
> setx HIP_VISIBLE_DEVICES 0
> ```
> Номер карты виден в `%LOCALAPPDATA%\Ollama\server.log`. Команда `rag eval` сама выгружает генератор перед запуском судьи и судью после оценки.

## Быстрый старт

Демо одной командой. Команда соберёт `demo_corpus/`, если его нет, запустит сервер, проиндексирует корпус и откроет интерфейс в браузере:

```bash
make demo          # или: python -m rag_agent.cli demo
```

Запуск по частям:

```bash
rag ui                                     # запустит сервер, если он не запущен, и откроет http://127.0.0.1:8765/
rag serve                                  # только сервер: API и интерфейс на 127.0.0.1:8765
```

Интерфейс — одна страница, которую отдаёт тот же локальный сервер ([`src/rag_agent/webui`](src/rag_agent/webui)). Шрифты и библиотеки лежат в репозитории, в сеть страница не обращается. Политика CSP запрещает загружать что-либо извне, какой бы текст ни пришёл в ответе. Две темы — тёмная и светлая холодная, «Сланец», — переключаются кнопкой у названия модели, по умолчанию как в системе. В «Параметрах» — четыре цвета акцента.

- **Слева.** Рабочая папка со статусом индекса, числом файлов и фрагментов, кнопкой «Индексировать» и настройками: типы файлов, исключения, системный диалог выбора папки, ранее проиндексированные папки. Каталог экспериментов. Список диалогов по дням.
- **В центре.** Ответ со ссылками-метками на источники, карточки источников (клик открывает фрагмент), свёрнутый черновик рассуждений, подтверждения действий агента, карточка код-агента с diff и кнопками «Отклонить» и «Применить».
- **Справа.** «Ход ответа» — шаги с временем: маршрутизатор, поиск, SQL, агент, веб, рассуждение, проверка ссылок, полная трасса. «Файлы сессии» — загруженные в диалог файлы и изменения, ждущие подтверждения. «Доступ агента». Вкладка «Настройки» (или кнопка с ползунками в шапке) — параметры каждой модели отдельно, с рекомендованными значениями рядом: для модели чата температура, top P, top K, штраф за повторы (действуют на свободный текст ответа; маршрутизатор, планы и JSON остаются на температуре 0), контекст и длина ответа; для генератора картинок шаги, CFG, сэмплер, расписание шума, сила перерисовки, негативный промпт, энкодер на процессоре, flash attention, VAE тайлами. Хранятся в `<data_dir>/model_settings.json`.

Диалоги хранятся на сервере (`dialogs.sqlite` в каталоге данных) вместе с ответами, источниками и трассой: открытый заново диалог выглядит так же, как при ответе. Файлы, загруженные в диалог, живут в его сессии сутки и попадают в рабочую папку только по кнопке «Добавить в корпус».

В интерфейсе выберите рабочую папку, при необходимости поправьте исключения и нажмите «Индексировать». Повторная индексация инкрементальная: разбираются только новые и изменённые файлы, удалённые убираются из индекса.

В чате можно задавать и вопросы по файлам, и общие вопросы. Переключатель «Источник ответа» в шапке диалога:

- **Авто.** Маршрутизатор сам решает, нужен ли поиск по файлам.
- **Мои файлы.** Ответ всегда по файлам, со ссылками.
- **Общие знания.** Ответ без поиска, как у обычного ассистента.

Уточняющие вопросы («а где она вызывается?») переписываются с учётом истории диалога в самостоятельный вопрос. «Новый диалог» начинает разговор без истории; старые диалоги остаются в списке.

Переключатель «Думать» управляет режимом рассуждений (Э12):

- **Выкл.** Быстрый ответ без рассуждения.
- **Вкл.** Модель сначала рассуждает, потом отвечает.
- **Авто** (по умолчанию). Маршрутизатор оценивает сложность вопроса: `none` — найти факт, `light` — сопоставить несколько фактов, `deep` — объяснить причину, проверить вывод, спланировать. От уровня зависит бюджет рассуждения: 512 или 1536 токенов.

Бюджет жёсткий: если рассуждение не уложилось, оно обрывается и модель сразу отвечает по черновику (budget forcing). Если быстрый ответ в авторежиме не подтверждён ссылками, он повторяется с рассуждением. Рассуждение показывается свёрнутым блоком «Черновик рассуждений». Это не объяснение ответа: подтверждение — только ссылки на источники. В историю диалога рассуждение не попадает.

### Один агент в чате

Отдельного режима «Код» нет: агент сам решает, как ответить.

- **Файлы, общие знания, интернет** — как описано выше: маршрутизатор, прямой поиск или агентный цикл (Э7), веб-шлюз (Э16).
- **Задачи, где нужно выполнить код** — построить и сохранить график, посчитать по логам, запустить скрипт, ноутбук или тесты, исправить ошибку, спарсить данные. Такую просьбу распознаёт отдельная проверка: регулярное выражение отбирает запросы с глаголами действия, модель подтверждает. Задача уходит код-агенту (Э15). Он работает в git-копии папки, запускает код в песочнице Docker, читает ошибки и исправляет. Из вывода его запусков модель пишет ответ: сами данные (таблицей, если это ряды значений), затем что сделано. Под ответом — карточка с diff, созданными файлами и кнопками «Отклонить» и «Применить». В папку пользователя ничего не попадает без «Применить».
- **Новая программа из нескольких модулей** («напиши по базе shop.db сервис отчётов», «сделай приложение для…»). Код-агент берёт задачу конвейером `project`:
  1. Читает данные в песочнице: таблицы и колонки SQLite, число строк, примеры строк, заголовки CSV.
  2. Составляет план: Python-пакет в отдельной папке в корне папки пользователя. В плане классы по слоям (модели-dataclass, репозиторий, сервисы, интерфейс — `argparse` и, если нужен сервис, HTTP API на `http.server`), тесты pytest, README, команды запуска и проверки.
  3. Пишет файлы по одному: каждый видит интерфейсы уже написанных.
  4. Проверяет: компиляция, тесты, команда проверки на данных пользователя. Если проверка упала, обычный цикл «запуск — ошибка — правка» получает вывод и план (до `code.project_max_steps` шагов). После исправлений проверка повторяется.
  5. Модель пишет ответ: что делает программа, архитектура, как запустить и прошли ли тесты.

  Цикл агента дописывает историю шагов, а не сдвигает окно. Сервер модели переиспользует кэш начала промпта и читает только новый шаг. Замер на промпте в 9 тыс. токенов: 64 с без кэша, 2 с с дописанным шагом, 40 с со сдвинутым окном. Выводы из неудачных запусков приходят вместе с ошибкой, а не в системном промпте. Старые выводы инструментов сокращаются разово, когда история перерастает ~90 тыс. символов. Повторное чтение того же фрагмента и шесть шагов подряд без правок и запусков агенту подсвечиваются: раньше модель, забыв прочитанное, ходила по кругу.

  Папка проекта появляется у пользователя после «Применить». Если имя занято, добавляется суффикс, чужие файлы не перезаписываются. Базы и таблицы (`.db`, `.sqlite`, `.parquet`, `.xlsx`) копируются в рабочую копию только для чтения: git их игнорирует, поэтому они не попадают ни в diff, ни обратно в папку пользователя.
- **Расчёт по ходу ответа.** Исследовательский агент Э7 получает инструмент `run_code`: фрагмент Python выполняется в песочнице над временной копией текстовых файлов папки, вывод становится источником ответа наравне с фрагментами и SQL.
- **Контекст.** Код-агент получает недавние реплики диалога и итоги прошлых запусков. «Попробуй ещё раз» продолжает прежнюю задачу, а на «что ты сделал?» есть ответ: в истории диалога хранится итог каждого запуска — файлы, статус, применил ли пользователь изменения.
- **Прикреплённые файлы** остаются в контексте диалога, пока их не убрать. Если вопрос не про файл, он маршрутизируется как обычно. На обзорный вопрос по длинному файлу («о чём он?») ответ строится по началу файла и началам его разделов.

Переключатель **«Сеть для кода»** под полем ввода разрешает песочнице выход в интернет: скачать данные, установить пакет командой `pip install` (в рабочую копию задачи, не в образ). Каждый запуск с сетью нужно подтвердить, на карточке задачи стоит метка «с сетью». Без переключателя песочница работает без сети, как требует NFR8. Отключить переключатель совсем — `code.network: never`. Выполнение кода в чате выключается в «Параметрах» или `code.chat: off`.

**Модель** выбирается кликом по её названию внизу слева: список моделей Ollama. Выбор действует на новые ответы в этом браузере и на код-агента. Индексация и каталог экспериментов остаются на модели из конфигурации (`llm.model`). Две модели по 16 ГБ одновременно в память видеокарты не помещаются, и Ollama выгружает прежнюю.

Ответы по умолчанию развёрнутые (`generation.style: detailed`): сначала суть, затем пояснения; ряды значений и сравнения оформляются таблицами. Формулы модель пишет в LaTeX (`$…$`, `$$…$$`, `\(…\)`, `\[…\]`), интерфейс отрисовывает их KaTeX. Строчная формула распознаётся, только если похожа на математику: цены вроде «$4,280 … $137» и `$PATH` остаются текстом. KaTeX работает без `trust`, так что `\href` и `\includegraphics` ничего не загружают. `concise` — краткий стиль замеров до Э17 включительно. Длина ответа — до 16 384 токенов (`llm.max_tokens`), окно модели — 65 536 токенов на промпт и ответ вместе (`llm.num_ctx`). У моделей семейства qwen35 KV-кеш маленький: 27B с таким окном занимает 16,3 ГБ видеопамяти против 16,1 ГБ при 16k. Файл, загруженный в диалог, подаётся в промпт целиком, пока он меньше трети окна (около 65 тыс. символов). Если ответ всё же упёрся в лимит, он помечается.

### Картинки: нарисовать, изменить, дорисовать

Необязательная локальная функция (`imagegen`, по умолчанию выключена). Генератор — [Qwen-Image-2.1](https://huggingface.co/Qwen/Qwen-Image-2.1) (7B DiT; рисует и редактирует одной моделью), движок — [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) (`sd-cli`, сборка Vulkan работает на AMD под Windows без ROCm).

- «Нарисуй…», «сгенерируй картинку…» — модель чата переписывает просьбу в промпт генератора (на английском, текст для надписи — как есть) и выбирает формат: квадрат, портрет, пейзаж.
- «Измени…», «перерисуй фон…», «сделай в стиле…» — правка последней нарисованной картинки или прикреплённой фотографии (картинка передаётся генератору как референс).
- Под картинкой: «Изменить» (следующее сообщение правит её), «Дорисовать область» (закрасить кистью то, что перерисовать, и описать, что там должно быть), «Расширить» (дорисовать за краями: выбранные стороны становятся шире на четверть; маска заходит полосой внутрь старой картинки, и при сборке старая картинка плавно переходит в новую — без шва по линии холста), «Скачать».
- Прикреплённые фото (PNG, JPEG, WebP) описываются VLM конвейера Э5: о них можно спрашивать, их можно править.
- Окно ввода и агент одни на всё: просьба о картинке распознаётся в том же чате. Слева под моделью чата — модель для картинок: кроме модели по умолчанию, в списке другие сборки той же модели (другое квантование, другой файн-тюн), лежащие рядом с ней или в `imagegen.models_dir`; текстовые энкодеры и VAE в список не попадают. Модель другого семейства или turbo-версия описывается в `imagegen.models` со своими VAE, текстовым энкодером, числом шагов, CFG, сэмплером и расписанием шума (`--scheduler`) — например, Krea2 turbo (архитектуру `krea2` поддерживает sd.cpp): 8 шагов, CFG 1, euler + simple. Устройство на карточке сообщает сам `sd-cli` (`--list-devices`), видеокарту на карточке модели чата — операционная система (WMI, nvidia-smi / lspci, system_profiler) или PyTorch: на другом компьютере там будет его карта.
- Кнопка «Размер» под полем ввода: «Авто» (формат выбирает модель чата, около 1 Мп — быстро), размеры из карточки модели (1:1 2048×2048, 4:3 2400×1792, 3:4, 3:2 2528×1696, 2:3, 16:9 2752×1536, 9:16), «Как у картинки» (для правки своей фотографии) или свой размер (стороны округляются до кратных 32, больше 4,2 Мп уменьшается с сохранением пропорций). Правка по описанию берёт размер как есть; дорисовка области и перерисовка сохраняют пропорции исходной картинки, а размер задаёт число пикселей. Предел времени генерации растёт с размером: картинка 2K считается в разы дольше 1K.

Генерация идёт отдельным процессом `sd-cli` на каждую картинку, модель чата на это время выгружается из Ollama. DiT считается на GPU, текстовый энкодер (Qwen3-VL-8B, bf16 — 17,5 ГБ) — на процессоре (`imagegen.text_encoder_on_cpu`): вместе они не помещаются в 24 ГБ, а перенос весов на GPU по мере расчёта (`imagegen.offload_to_cpu`, `--offload-to-cpu`) в сборке Vulkan добавляет ~4 минуты на подготовку. При правке по референсу энкодер читает и саму картинку (сотни токенов), поэтому его веса лежат в оперативной памяти, а считает GPU (`--params-backend te=cpu`). Время на RX 7900 XTX (20 шагов): новая картинка 1216×832 — ~1,5–2 мин, дорисовка области — ~2 мин, расширение до 1824×832 — ~3 мин, правка по референсу (1024×672) — ~2,5 мин; с энкодером int8 или GGUF Q4 подготовка короче. CFG — 3 (`imagegen.cfg_scale`): при 6 из документации sd.cpp картинка темнеет, тени «сгорают» и появляются вертикальные полосы с шагом 8 px (их сила по спектру: 117 при CFG 6, 44 при 4, 23 при 3; на Vulkan и ROCm одинаково — это свойство модели, а не бэкенда). Больше шагов (`imagegen.steps`, у модели рекомендовано 40) дают резче детали ценой времени: 40 шагов вдвое дольше 20. VAE декодирует тайлами (`imagegen.vae_tiling`): без них сборка Vulkan не выделяет буфер декодера и уходит на процессор. Маленькие фото перед правкой увеличиваются до ~1024 px по длинной стороне: модель рисует детально около мегапикселя. `sd-cli` под Windows не открывает пути с кириллицей, поэтому входы и результат лежат во временной папке с ASCII-путём (`imagegen.work_dir`). Картинки хранятся по диалогам в `<data_dir>/generated/` и удаляются вместе с диалогом.

Просьбы с сексуальным контентом с участием несовершеннолетних отклоняются до генерации: проверку делает модель чата при разборе просьбы, и дублирует словарная проверка.

Модели проще всего класть в папку `models/` проекта ([models/README.md](models/README.md)): `models/image/<модель>/` — диффузионная модель, её VAE и текстовый энкодер лежат вместе и находятся сами (семейство — по метаданным GGUF или имени), настройки по умолчанию — по семейству (turbo-сборки: 8 шагов, CFG 1). Настройки каждой модели, заданные в интерфейсе, хранятся в `<data_dir>/model_settings.json` поверх рекомендованных. В `configs/local.yaml` остаются включение, путь к `sd-cli` и, при желании, модели вне `models/` (пути не попадают в репозиторий):

```yaml
imagegen:
  enabled: true
  sd_cli: C:/ml-models/sd-cpp/sd-cli.exe
  diffusion_model: C:/ml-models/qwen-image-2.1/qwen-image-2.1-Q6_K.gguf
  vae: C:/ml-models/qwen-image-2.1/qwen_image_2.1_vae_bf16.safetensors
  llm: C:/ml-models/qwen-image-2.1/qwen3vl_8b_bf16.safetensors   # или Qwen3VL-8B-Instruct-Q4_K_M.gguf
  # models_dir: D:/models/qwen-image   # ещё сборки модели для выбора в UI (необязательно)
  models:                              # модели со своими файлами и сэмплингом (необязательно)
    - path: C:/ml-models/krea2-turbo/Krea2_turbo-Q4_K_M.gguf
      vae: C:/ml-models/krea2-turbo/qwen_image_vae.safetensors
      llm: C:/ml-models/krea2-turbo/qwen3vl_4b_fp8_scaled.safetensors
      steps: 8
      cfg_scale: 1.0
      sampler: euler
      scheduler: simple
```

### Видео: снять ролик, оживить картинку

Генератор — LTX-2 (видео со звуком) через `sd-cli -M vid_gen`, выход `.webm`. Включается сам, когда в `models/video/<модель>/` лежат модель, VAE видео, VAE звука, текстовый энкодер (Gemma) и коннекторы эмбеддингов (для LTX-2.3), а `imagegen.sd_cli` указан.

- «Сними видео…», «анимируй…», «оживи картинку» — модель чата пишет промпт генератора: что в кадре, движение камеры, звук; длительность — из просьбы (кадров 8k + 1: 3 с при 24 к/с — 73), иначе из настроек.
- «Анимируй, как она едет» после нарисованной картинки или с прикреплённым фото — картинка становится первым кадром (image-to-video); кнопка «Оживить» под картинкой делает то же.
- Слева над моделью картинок — карточка видеомодели; во вкладке «Видео» панели настроек — кадры, fps, площадь кадра, шаги, CFG, сэмплер, негативный промпт, энкодер на процессоре (22B-модель и 12B-энкодер вместе не помещаются в 24 ГБ), веса в оперативной памяти.
- Ролики хранятся по диалогам в `<data_dir>/videos/` и удаляются вместе с диалогом; просьбы с сексуальным контентом с участием несовершеннолетних отклоняются, как и для картинок.

## Как устроено

```
файлы ─► walker (исключения) ─► парсеры .py (AST) / .ipynb (граф ячеек) / .pdf (Docling, OCR) / .docx / .txt ─► узлы + связи
        ─► BGE-M3 (dense + sparse) ─► Qdrant                            ┐
        ─► SQLite-каталог (files, nodes, edges, symbols, calls)         ┘

вопрос (+ история) ─► маршрутизатор ─┬─ corpus  ─► поиск ─► LLM (JSON: answerable, answer [n], general) ─► ответ с цитатами
                                     └─ general ─► LLM ─► ответ из общих знаний

поиск: BGE-M3 dense (top-40) ─► реранкер bge-reranker-v2-m3 ─► RRF с определениями и вызовами имён из вопроса ─► top-6
```

- **Единая модель данных** (`schema.py`). Файл разбирается на узлы: фрагмент кода, markdown-ячейка, ячейка кода, вывод ячейки и т. д. Между узлами хранятся типизированные связи: `contains`, `produces` (ячейка → её вывод) и другие.
- **Ноутбуки — граф ячеек.** Каждая ячейка становится отдельным узлом. Вывод ячейки — тоже отдельный узел: он обрезается с сохранением хвоста, где обычно стоят итоговые метрики, и индексируется вместе с кодом, который его породил (связь `produces`). В заголовок каждой ячейки добавляется название ноутбука и путь по разделам («Бейзлайн: логистическая регрессия > Обучение»). Связи `uses_var` показывают, из какой ячейки пришла переменная: это статическая нижняя оценка потоков данных, как в синтаксической стадии CRABS.
- **Код `.py` — AST-чанкинг** в духе cAST. Функции и классы не разрезаются, мелкие соседние определения склеиваются до лимита. Большой класс делится на заголовок и группы методов, у каждой группы в контексте указан класс. Декораторы и комментарии над функцией остаются с ней. Нарезка окнами по строкам осталась как бейзлайн: `chunking.python: lines`.
- **Символы и вызовы.** Статический анализ собирает определения функций и классов и места вызовов, включая ячейки ноутбуков. Из них строится точный поиск имён: если в вопросе есть имя из корпуса, в выдачу добавляются его определение и места вызова. Та же таблица отвечает на вопрос «где вызывается X» без LLM: `rag symbols X`.
- **PDF** разбирается Docling: модель вёрстки на DocLayNet восстанавливает порядок чтения многоколоночных страниц, TableFormer — структуру таблиц. Узлы — разделы с диапазоном страниц, таблицы в Markdown, рисунки с подписями. OCR (EasyOCR, ru/en) запускается, только если у страниц нет текстового слоя.
- **DOCX** читается из XML без моделей: иерархия заголовков, таблицы, рисунки с подписями, свойства документа. Правки в режиме рецензирования принимаются в действующем тексте, а удалённое и вставленное хранится отдельными узлами, как и комментарии рецензентов. Их можно найти по прямому вопросу («какие правки вносились?»), но с действующим текстом они не смешиваются.
- **Изображения** (Э5): `.png` и `.jpg`, картинки в выводах ячеек ноутбуков, рисунки PDF и DOCX становятся узлами-изображениями. После индексации каждое проходит конвейер (`images/`): тип определяет дообученная MobileNetV3-Small (график, схема, скриншот, скан, фото); скриншоты и сканы читает EasyOCR; VLM описывает картинку по её типу — график переводится в таблицу с осями и трендом (идея DePlot), схема — в список блоков и связей. Описание индексируется как текст узла и кешируется по хешу картинки. Дополнительно можно построить визуальный индекс ColQwen2 по картинкам и страницам PDF (`images.visual_index`, канал `images.channel: fusion`, H4).
- **TXT, MD, LOG.** Кодировка определяется автоматически (Windows-1251 тоже). Тип содержимого определяется эвристикой: markdown, лог, таблица, код, проза. Из логов обучения извлекаются метрики по эпохам — лучшее и последнее значение — в отдельный узел-сводку.
- **Поиск.** Первая стадия — плотный поиск BGE-M3; режимы `sparse` и `hybrid` доступны, но на демо-корпусе не помогли. Затем кросс-энкодер переупорядочивает 40 кандидатов, и в конце результаты сливаются через RRF с точными совпадениями имён.
- **Индексы.** Для каждой комбинации «папка × эмбеддер × настройки чанкинга» создаётся отдельный индекс. Поэтому абляции переключаются без переиндексации ранее построенных вариантов.
- **Маршрутизатор** (`router.py`) одним вызовом LLM со structured output выбирает маршрут `corpus` или `general` и переписывает уточняющий вопрос в самостоятельный. При сомнении выбирается `corpus`. Если ни одна папка не проиндексирована, ответ даётся из общих знаний с пометкой.
- **Ответ.** Генерация идёт со structured output: JSON-схема, декодирование ограничено сервером. Ссылки `[n]`, не соответствующие найденным фрагментам, удаляются. Если ответа в найденном нет, модель должна отказаться.

```
src/rag_agent/
  config.py        настройки: configs/default.yaml < configs/local.yaml < RAG__SECTION__KEY
  schema.py        узлы, связи, локации
```

## Оценка качества

```bash
rag eval                                   # демо-набор, ответы + LLM-судья
rag eval --retrieval-only --mode hybrid    # только метрики поиска
rag eval путь/к/набору.yaml --no-judge     # свой набор, без судьи
rag eval-validate путь/к/набору.yaml       # проверить разметку по индексу
rag ablate configs/ablations/e3.yaml       # таблица абляций: несколько конфигураций на одном наборе
rag rejudge configs/ablations/e13.yaml runs/ablations/<папка>   # заново к судье, ответы не генерируются
rag ablate-code configs/ablations/e15.yaml # код-агент: задачи со скрытыми проверками в песочнице
python scripts/redteam_code.py             # опасный код в песочнице (Э17), без модели
python scripts/h9_monitoring.py            # мониторинг на канареечных запросах (Э9, pip install driftfdr)
make check                                 # секреты и личные пути в файлах репозитория (то же в CI)
```

По умолчанию используется `evalsets/demo_v4.yaml` (Э12: документы и 16 вопросов, требующих рассуждения); наборы прежних этапов — `demo_v3.yaml` (Э4), `demo_v2.yaml` (Э3) и `demo_v1.yaml` (Э2). Результаты пишутся в `runs/eval/<дата>-<имя>-<режим>/`: `report.md`, `summary.json`, `results.jsonl`, `config.json`. Папка `runs/` не коммитится.

Считаются метрики из раздела 5.2 ТЗ:

- **Поиск:** Recall@k, Hit@k, MRR, nDCG@10, в разрезе классов и типов файлов.
- **Маршрутизатор:** точность.
- **Ответы:** обязательные элементы ответа, корректность и верность контексту по оценке LLM-судьи, точность цитирования (по разметке и по судье), релевантность.
- **Отказы:** precision и recall отказов на неотвечаемых вопросах (Q6).
- **Латентность:** p50 и p95.
- **Рассуждения:** точность против сгенерированных токенов и задержки по классам вопросов, доля вопросов с рассуждением, доля обрезанных по бюджету, доля лишних токенов без прироста точности.

Для основных метрик считается 95% бутстреп-интервал.

**Свой эталонный набор** для приватного корпуса — главный артефакт проекта (ТЗ, S9). Формат описан в шапке [evalsets/demo_v1.yaml](evalsets/demo_v1.yaml). Эталонные источники задаются как `{file, cell}` или `{file, lines}`, поэтому разметка не зависит от способа чанкинга и переживает абляции. Кладите приватные наборы в `evalsets/private/`, эта папка не коммитится.

## Конфигурация

Все параметры задаются в `configs/default.yaml`. Для машинно-специфичных настроек создайте `configs/local.yaml`, он не коммитится. Любой ключ можно переопределить переменной окружения, например `RAG__LLM__MODEL=qwen3.6:27b` или `RAG__RETRIEVAL__MODE=hybrid`.

## Приватность

- Индексы, каталоги и трассы хранятся в `~/.local-rag-agent`, вне репозитория.
- Собственный репозиторий и каталог данных никогда не индексируются, даже если лежат внутри выбранной папки.
- Папки с чувствительными данными добавляйте в исключения. По умолчанию уже исключены `Аккаунты`, а также `.git`, окружения и все скрытые папки.
- Содержимое файлов подаётся модели как данные. Промпт запрещает выполнять инструкции из фрагментов.
- Интерфейс не загружает ничего из интернета: шрифты (Manrope, Fira Code — OFL) и библиотеки (marked — MIT, DOMPurify — Apache-2.0 / MPL-2.0, KaTeX — MIT) лежат в [`src/rag_agent/webui`](src/rag_agent/webui) вместе с лицензиями. Текст ответов проходит через DOMPurify, а политика CSP запрещает внешние запросы страницы.
