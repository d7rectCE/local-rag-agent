# Мультимодальный агент над корпусом исследовательских файлов: анализ литературы и техническое задание

Документ объединяет две части технического задания магистерского проекта: основу — вопросно-ответную систему с цитированием над корпусом `.py`, `.ipynb`, `.pdf`, `.png` (этапы Э1–Э10) — и рабочего ассистента с новыми форматами, рассуждением, загрузками, исполнением кода и интернетом (этапы Э11–Э17). Сначала — анализ литературы по обеим частям (раздел 1). Из его выводов сформировано техническое задание (раздел 2): проблемы кейса, решения, методология оценки, требования, этапы и риски. Ссылки вида [n] ведут в общий список литературы (раздел 3). Состояние этапов и результаты проверки гипотез — в [README](../README.md) и [отчётах](../reports).

## 1. Анализ литературы

**Методика отбора.** Источниками служили публикации рецензируемых конференций и журналов (NeurIPS, ICLR, ACL, EMNLP, NAACL, EACL, KDD, SIGIR, USENIX Security, COLM, TACL, статистические журналы) и препринты исследовательских групп на arXiv. Блоги, форумы и маркетинговые материалы не использовались. Хронологический охват — 1954–2025 годы: классические статистические работы по обнаружению изменений и множественной проверке гипотез и, с акцентом, работы 2023–2025 годов. Обзор организован по компонентам будущей системы; в конце каждого раздела сформулирован вывод для проекта.

**Методика отбора** та же, что в Части 1: рецензируемые конференции и журналы (NeurIPS, ICLR, ICML, ACL, EMNLP, NAACL, COLM, NSDI, VEE, Nature, Computational Linguistics, TACL) и препринты исследовательских групп на arXiv. Блоги, форумы и документация продуктов не использовались. Работы, уже разобранные в Части 1, здесь упоминаются, только когда они нужны для новых решений.

### 1.1. Генерация с извлечением: базовые работы и обзоры

Lewis и соавт. [1] предложили объединять параметрическую память языковой модели с непараметрической памятью в виде плотного индекса документов и показали прирост на задачах, требующих знаний. Обзор Gao и соавт. [2] систематизировал эволюцию подхода от «наивного» RAG (индексация, поиск, генерация) через «продвинутый» (предварительная и последующая обработка запроса и найденного) к модульному, где компоненты заменяемы и комбинируются. Систематический обзор Brown и соавт. [3] охватывает наиболее цитируемые работы 2020–2025 годов и классифицирует техники, метрики и нерешённые проблемы.

**Вывод для проекта:** архитектура должна быть модульной, а качество каждого модуля должно измеряться отдельно. Итоговое качество ответа ограничено сверху качеством поиска.

### 1.2. Поиск: плотный, разреженный, гибридный

Karpukhin и соавт. [4] показали, что плотный поиск с двумя энкодерами (DPR) превосходит BM25 на задачах open-domain QA. Однако бенчмарк BEIR [5] продемонстрировал, что в режиме zero-shot на новых доменах BM25 остаётся сильным базовым методом, а плотные модели нередко ему проигрывают. Для нашего корпуса это критично: он сугубо доменный и насыщен идентификаторами, аббревиатурами и названиями библиотек.

Модель BGE-M3 [6] в одной сети реализует три режима — плотный, разреженный (лексический) и мультивекторный — поддерживает более 100 языков и входы до 8192 токенов. Это закрывает требования к мультиязычности и гибридному поиску без отдельного лексического индекса. Мультивекторный режим восходит к ColBERT [7], где сопоставление запроса и документа выполняется поздним взаимодействием на уровне токенов.

Точность top-k повышается переранжированием кросс-энкодером [8], который совместно кодирует запрос и документ. Для слияния списков от разных поисковиков стандартом служит Reciprocal Rank Fusion [9], не требующий калибровки оценок. Для коротких и недоопределённых запросов применяется переформулирование: HyDE [10] генерирует гипотетический документ-ответ и ищет по его эмбеддингу.

**Вывод для проекта:** базовая конфигурация — гибридный поиск (плотный и разреженный) со слиянием через RRF и переранжированием кросс-энкодером; для идентификаторов кода нужен отдельный точный поиск.

### 1.3. Разбиение на фрагменты (чанкинг)

Qu и соавт. [11] систематически сравнили семантический чанкинг (по порогам семантической близости соседних предложений или кластеризацией) с простым фиксированным на трёх задачах: поиск документа, поиск доказательства и генерация ответа. Вычислительные затраты семантического чанкинга не окупаются стабильным приростом качества. RAPTOR [12] предлагает строить поверх фрагментов дерево рекурсивных суммаризаций; это помогает на вопросах, требующих обобщения по большому документу.

**Вывод для проекта:** для прозы достаточно структурного чанкинга по разметке, извлечённой из документа (заголовки, разделы, абзацы), без дорогого семантического. Для вопросов уровня «о чём этот ноутбук» полезны иерархические суммаризации.

### 1.4. Код и Jupyter-ноутбуки

Zhang и соавт. [13] предложили cAST — чанкинг по абстрактному синтаксическому дереву. Крупные узлы рекурсивно разбиваются, мелкие соседние объединяются в пределах лимита размера. По сравнению с построчным чанкингом метод повысил Recall@5 на RepoEval на 4,3 пункта и Pass@1 на SWE-bench на 2,67 пункта. Авторы отдельно указывают на потенциал многоракурсного представления фрагмента кода: код, комментарии и описание на естественном языке. RepoCoder [14] показал эффективность итеративного поиска по репозиторию, при котором промежуточная генерация служит запросом для следующего шага поиска.

Для ноутбуков показательна работа Li и соавт. [15] (COLM 2025). В базовом варианте, когда весь ноутбук целиком подаётся LLM с тщательно составленным промптом, модель полностью не справилась с 20% ноутбуков из выборки Kaggle — длинных, в среднем по 52 ячейки. Предложенная стратегия CRABS сначала выполняет неглубокий синтаксический анализ AST и получает нижнюю и верхнюю оценки потоков данных между ячейками, а затем разрешает оставшиеся неоднозначности LLM по одной ячейке. Так достигается F1 около 98% при восстановлении информационных потоков. Grotov и Titov [16] (ICLR 2025) показали, что современные LLM плохо используют runtime-информацию ноутбуков, то есть выводы ячеек и состояние переменных.

**Вывод для проекта:** ноутбук следует рассматривать не как текст, а как граф ячеек с зависимостями и привязанными выводами. Синтаксический препроцессинг обязателен, LLM применяется локально к ячейкам, а не ко всему файлу.

### 1.5. Документы и изображения: вёрстка, OCR, визуальный поиск

DocLayNet [17] — датасет из 80 863 вручную размеченных страниц шести категорий документов с 11 классами элементов вёрстки. Он стал стандартом для обучения детекторов layout. Docling [18] — открытый конвейер конвертации PDF, использующий модель вёрстки, обученную на DocLayNet, и модель распознавания структуры таблиц TableFormer. Конвейер рассчитан на обычное оборудование. Альтернативную ветвь представляют OCR-free модели, которые понимают документ напрямую из изображения без явного распознавания текста [19].

ColPali [20] (ICLR 2025) вводит принципиально иной подход. Вместо разбора документа эмбеддинги строятся VLM непосредственно по изображению страницы, а сопоставление с запросом идёт через позднее взаимодействие в стиле ColBERT. На бенчмарке ViDoRe такой подход существенно превосходит конвейеры разбора, будучи проще и быстрее. VisRAG [21] (ICLR 2025) распространяет идею на весь конвейер: и поиск, и генерация работают с изображениями страниц. Авторы сообщают о приросте 20–40% end-to-end относительно текстового RAG на мультимодальных документах.

Для графиков применимы работы по их пониманию. ChartQA [22] — бенчмарк вопросов по графикам, требующих визуального и логического рассуждения. DePlot [23] переводит график в таблицу, по которой затем рассуждает LLM. Это позволяет индексировать содержимое графика как структурированный текст.

**Вывод для проекта:** существуют два конкурирующих подхода — «разобрать, затем индексировать текст» и «индексировать изображение напрямую». Их сравнение на собственном корпусе — содержательный эксперимент. Для графиков перспективен перевод в таблицу.

### 1.6. Структурированные запросы: text-to-SQL

Spider [24] задал стандарт кросс-доменного text-to-SQL. BIRD [25] (NeurIPS 2023) приблизил постановку к реальности: 12 751 пара «вопрос–SQL» над 95 базами общим объёмом 33,4 ГБ из 37 предметных областей, с «грязными» значениями и необходимостью внешних знаний. На момент публикации GPT-4 достигал 54,89% точности исполнения против 92,96% у человека.

CHESS [26] решает проблему больших схем модульным конвейером. Значения из базы извлекаются через locality-sensitive hashing по ключевым словам запроса, описания таблиц и колонок — через векторный поиск по каталогу. Затем схема сужается с сотен колонок обычно до менее чем десяти, и только после этого генерируется и проверяется SQL.

**Вывод для проекта:** агрегатные вопросы решаются не поиском фрагментов, а запросами к реляционному каталогу. Описания колонок и характерные значения нужно индексировать, а в промпт подавать суженную схему.

### 1.7. Агентные системы

ReAct [27] (ICLR 2023) чередует шаги рассуждения и действия с инструментами. Это базовый паттерн агентов с инструментами. Self-RAG [28] (ICLR 2024) обучает модель самой решать, когда нужен поиск, и критиковать найденное и собственный ответ специальными токенами рефлексии. Corrective RAG [29] добавляет лёгкий оценщик качества найденных документов: при низкой оценке запускаются корректирующие действия — переформулирование запроса или смена источника.

Обзор Singh и соавт. [30] систематизирует агентный RAG через паттерны рефлексии, планирования, использования инструментов и мультиагентного взаимодействия. Для вопросов, требующих глобального обобщения по корпусу, предложен GraphRAG [31], строящий граф сущностей и иерархию сообществ.

**Вывод для проекта:** достаточно одного агента ReAct с ограниченным набором инструментов и явной проверкой релевантности найденного. Мультиагентная схема для корпуса такого размера избыточна.

### 1.8. Адаптация моделей

LoRA [32] обучает низкоранговые добавки к весам при замороженной базовой модели. QLoRA [33] (NeurIPS 2023) сочетает это с 4-битной квантизацией базовой модели, что позволяет дообучать модели в несколько миллиардов параметров на одной GPU. RAFT [34] (COLM 2024) обучает LLM отвечать по доменным документам при наличии в контексте нерелевантных «отвлекающих» фрагментов и цитировать нужный фрагмент; это повышает устойчивость в доменном RAG.

Для дообучения поисковиков без ручной разметки Promptagator [35] (ICLR 2023) генерирует синтетические запросы к документам с помощью LLM по нескольким примерам и фильтрует их по согласованности: сгенерированный запрос должен находить свой исходный документ.

**Вывод для проекта:** главный рычаг адаптации — синтетические пары «запрос–фрагмент», порождённые из собственного корпуса. Они служат и для дообучения эмбеддера, и для расширения набора оценки, и, как показано в разделе 4, для мониторинга в эксплуатации.

### 1.9. Оценка качества

RAGAS [36] (EACL 2024) предлагает набор метрик без эталонных ответов: верность ответа контексту (faithfulness), релевантность ответа и релевантность контекста. Zheng и соавт. [37] (NeurIPS 2023) показали, что сильная LLM-судья согласуется с людьми на уровне, сопоставимом с согласием людей между собой. Однако ей присущи систематические смещения: зависимость от позиции ответа, предпочтение более длинных ответов и завышение оценок собственных ответов.

Liu и соавт. [38] (TACL 2024) обнаружили эффект «потери в середине»: качество использования длинного контекста максимально, когда релевантная информация находится в начале или конце, и заметно падает, когда она в середине. Для оценки поиска стандартны метрики nDCG@10 и Recall@k [5].

**Вывод для проекта:** поиск и генерацию оценивать раздельно; LLM-судью калибровать на ручной выборке и рандомизировать порядок; число фрагментов в контексте ограничивать.

### 1.10. Безопасность и приватность

Zeng и соавт. [39] (Findings of ACL 2024) экспериментально показали уязвимость RAG-систем к извлечению содержимого приватной базы через специально составленные запросы. Qi и соавт. [40] продемонстрировали масштабируемое извлечение данных из RAG-систем с помощью инструкций во входе. Greshake и соавт. [41] (AISec 2023) описали непрямые prompt-инъекции: инструкции, размещённые внутри извлекаемого контента, перехватывают управление LLM-приложением.

PoisonedRAG [42] (USENIX Security 2025) показывает, что небольшое число внедрённых в базу текстов способно навязать системе заданный ответ. Carlini и соавт. [43] (USENIX Security 2021) показали, что языковые модели запоминают и воспроизводят фрагменты обучающих данных.

**Вывод для проекта:** любой файл корпуса — недоверенный вход для агента, особенно ноутбуки и PDF из внешних источников. Веса, дообученные на приватных данных, нельзя публиковать.

### 1.11. Мониторинг деградации и контроль ложных тревог

Обзор Gama и соавт. [44] систематизирует методы обнаружения дрейфа концепции и адаптации к нему. Классические детекторы — CUSUM и его вариант Page-Hinkley [45], ADWIN [46] — выдают бинарный сигнал по порогу на внутренней статистике. Фактическая частота ложных срабатываний при этом неизвестна, особенно на автокоррелированных потоках.

Rabanser и соавт. [47] (NeurIPS 2019) эмпирически сравнили методы обнаружения сдвига распределения входных данных. Однако сдвиг входов не обязательно вреден для модели. Podkopaev и Ramdas [48] (ICLR 2022) предложили последовательный тест гипотезы о том, что риск развёрнутой модели вырос больше заданного допуска. Такой тест срабатывает только на вредные сдвиги и остаётся корректным в любой момент наблюдения. Это обосновывает мониторинг ошибки модели, а не её входов, и нулевую гипотезу с допуском вместо гипотезы «ничего не изменилось».

При мониторинге многих рядов ложные тревоги складываются. Классические средства контроля — процедура Benjamini–Hochberg [49] для доли ложных открытий и онлайн-правила вида LORD [50] для последовательно поступающих гипотез. Rombouts и Wilms [51] описали практический мониторинг прогнозных моделей по 32 районам платформы, где каждый район проверяется на уровне 5% без поправки на множественность. Dandapanthula и Ramdas [52] показали, что в многопоточном последовательном обнаружении изменений классические FDR и FWER при конечном среднем времени до ложной тревоги в худшем случае вырождаются, и предложили альтернативную меру ошибки. Shin и соавт. [53] ввели e-детекторы — непараметрическую схему последовательного обнаружения изменений.

Калибровка порогов по данным требует бутстрепа, сохраняющего зависимость наблюдений: блочного [54] или авторегрессионного sieve-бутстрепа [55]. Обычный бутстреп на автокоррелированном ряду занижает разброс статистики и, как следствие, даёт больше ложных тревог, чем заявлено.

**Вывод для проекта:** мониторить следует ошибку компонентов с нулевой гипотезой о существенном ухудшении; порог каждого детектора калибровать с учётом автокорреляции; решение по всем рядам принимать с поправкой на их число; общую для всех рядов составляющую (например, смену эмбеддера) выделять и проверять отдельно.

### 1.12. Разбор DOCX и TXT

Обзор методов разбора документов Zhang и соавт. [57] делит подходы на конвейерные (анализ вёрстки, затем распознавание содержимого) и сквозные на основе VLM. Оба направления рассчитаны на форматы, где структура утеряна и её приходится восстанавливать по изображению, то есть на PDF и сканы. Для DOCX ситуация обратная: структура явно записана в XML — стили заголовков, списки, таблицы, комментарии, исправления. Её достаточно прочитать декларативно, без моделей зрения. Открытый инструментарий Docling [56] разбирает разные форматы в единое представление документа, что позволяет обрабатывать DOCX и PDF одной моделью данных.

TXT — противоположный случай: структуры нет вовсе. Классический метод TextTiling [58] делит текст на тематические фрагменты по изменению лексического сходства соседних блоков. Он служит ориентиром для текстов без разметки. Chen и соавт. [59] (EMNLP 2024) показали, что более мелкие единицы индекса — пропозиции, то есть атомарные утверждения, — улучшают плотный поиск. Однако их получение требует вызова LLM на каждый фрагмент. Qu и соавт. [11] показали, что дорогой семантический чанкинг не даёт стабильного выигрыша над простым.

**Вывод для проекта:** DOCX разбирается декларативно, и все его структурные элементы переводятся в модель узлов из Части 1. Для TXT нужны определение кодировки и типа содержимого, а затем дешёвая сегментация по абзацам или по сменам темы. Пропозиции оправданы лишь как эксперимент на небольшом подмножестве.

### 1.13. Режим рассуждений

Цепочка рассуждений (chain-of-thought) [60] повышает точность на многошаговых задачах, а самосогласованность [61] — голосование по нескольким цепочкам — повышает её ещё больше ценой кратного роста вычислений. Snell и соавт. [62] (ICLR 2025) показали, что оптимальный объём вычислений при выводе зависит от сложности запроса. Распределение бюджета по запросам повышает эффективность более чем в 4 раза относительно best-of-N. На задачах, где базовая модель уже имеет заметный успех, малая модель с дополнительными вычислениями может превзойти модель в 14 раз больше.

DeepSeek-R1 [63] (Nature, 2025) показал, что длинные рассуждения можно выработать обучением с подкреплением по проверяемой награде. Muennighoff и соавт. [64] (EMNLP 2025) предложили budget forcing — принудительное ограничение или продление рассуждения на этапе декодирования, что даёт управляемый компромисс между точностью и затратами. Семейство Qwen3 [65] объединяет режимы с рассуждением и без него в одной модели и вводит бюджет рассуждений. Для одной GPU это важно: не нужно держать в памяти две модели.

У рассуждений есть обратная сторона. Chen и соавт. [66] (ICML 2025) описали «передумывание»: модели тратят непропорционально много токенов на простые задачи без прироста точности. Turpin и соавт. [67] (NeurIPS 2023) показали, что цепочка рассуждений не всегда отражает реальные причины ответа: при внесённом смещении точность падала до 36%, а модели не упоминали это смещение в рассуждениях. Chen и соавт. [68] воспроизвели эффект на рассуждающих моделях: доля случаев, когда модель упоминает использованную подсказку, часто ниже 20%.

**Вывод для проекта:** рассуждения должны включаться по сложности запроса и ограничиваться бюджетом. Текст рассуждения можно показывать пользователю как черновик, но нельзя выдавать за объяснение или доказательство. Доказательством остаются ссылки на источники.

### 1.14. Работа с загруженными файлами: длинный контекст или поиск

Для загруженного файла есть два пути: подать его в контекст целиком или проиндексировать и искать фрагменты. Li и соавт. [70] (EMNLP 2024) сравнили эти подходы. Длинный контекст в среднем точнее, но RAG многократно дешевле. Предложенный ими Self-Route сначала пробует RAG и позволяет модели самой объявить, что найденного недостаточно, — тогда запрос уходит в длинный контекст. Такой гибрид достигает качества длинного контекста при заметно меньших затратах.

Заявленная длина контекста при этом не равна эффективной. Бенчмарк RULER [71] (COLM 2024) показал, что качество многих моделей заметно падает задолго до заявленного предела. Эффект «потери в середине» [38] дополнительно снижает использование информации из центральной части длинного контекста. Adaptive-RAG [69] (NAACL 2024) обучает небольшой классификатор сложности запроса, который выбирает стратегию: без поиска, одношаговый поиск или итеративный.

**Вывод для проекта:** небольшой загруженный файл подаётся в контекст целиком, если укладывается в эффективный, а не заявленный бюджет. Большой индексируется во временный индекс сессии, а переключение между путями строится по схеме Self-Route.

### 1.15. Код-агенты

SWE-bench [72] (ICLR 2024) задал стандарт оценки код-агентов на реальных задачах из GitHub-репозиториев с проверкой тестами. SWE-agent [73] (NeurIPS 2024) показал, что интерфейс «агент — компьютер» (agent-computer interface, ACI) — специализированные команды просмотра файла с номерами строк, поиска и правки с проверкой синтаксиса — существенно влияет на успех. На момент публикации агент решал 12,5% задач SWE-bench, намного больше неинтерактивных подходов.

CodeAct [74] (ICML 2024) предлагает использовать исполняемый Python как единое пространство действий агента вместо JSON-вызовов. На 17 моделях это давало до 20% прироста доли успешно решённых задач. OpenHands [75] (ICLR 2025) — открытая платформа код-агентов с исполнением кода в песочнице, командной строкой и браузером. Agentless [76] показал, что фиксированный конвейер «локализация → исправление → проверка» без свободного агентного цикла конкурентоспособен при меньшей стоимости.

Обратная связь от исполнения — ключевой механизм. Self-Debugging [77] (ICLR 2024) учит модель исправлять код по результатам запуска и собственному объяснению кода. Reflexion [78] (NeurIPS 2023) сохраняет словесные выводы из неудачных попыток для следующих. Для кода анализа данных, типичного для корпуса из ноутбуков, существует бенчмарк DS-1000 [79] (ICML 2023) с задачами на pandas, NumPy, scikit-learn и другие библиотеки.

**Вывод для проекта:** агент действует кодом, получает специализированные инструменты просмотра и правки, обязательно видит результаты исполнения и ограничен числом итераций. Для типовых задач выгоднее фиксированный конвейер, чем свободный агент.

### 1.16. Доступ в интернет

WebGPT [80] и Toolformer [81] (NeurIPS 2023) показали, что языковая модель может научиться вызывать поиск и опираться на найденное. Mallen и соавт. [82] (ACL 2023) установили, что внешний поиск помогает прежде всего на малоизвестных фактах, а на популярных может даже навредить. Отсюда адаптивное решение, когда искать. FreshLLMs [83] (Findings of ACL 2024) показал, что все модели плохо справляются с быстро меняющимися фактами и ложными предпосылками, а число и порядок найденных фрагментов в промпте сильно влияют на точность.

Search-o1 [84] встраивает поиск прямо в процесс рассуждения: модель запрашивает поиск, когда встречает пробел в знаниях, а отдельный модуль Reason-in-Documents сначала анализирует найденные документы и лишь затем передаёт выжимку в цепочку рассуждений. Это снижает шум. Search-R1 [85] обучает такое поведение обучением с подкреплением.

Качество ответов с цитированием интернет-источников ограничено. Liu и соавт. [86] (Findings of EMNLP 2023) проверили четыре генеративных поисковика: только 51,5% сгенерированных предложений полностью подтверждались цитатами, и лишь 74,5% цитат подтверждали свои утверждения. Xie и соавт. [87] (ICLR 2024) показали двойственное поведение моделей при конфликте знаний: убедительный внешний текст они принимают даже вопреки своим знаниям, но при смешанных свидетельствах проявляют предвзятость подтверждения. Wang и соавт. [88] разработали методы RAG при противоречивых свидетельствах.

**Вывод для проекта:** искать в интернете нужно адаптивно, а не на каждый запрос. Найденное следует сначала сжимать и фильтровать, каждое утверждение — проверять на подкреплённость цитатой, а конфликты между корпусом и интернетом — показывать пользователю явно.

### 1.17. Безопасность агентов с инструментами

Greshake и соавт. [41] (AISec 2023) описали непрямые инъекции в промпт: инструкции внутри веб-страницы или документа, которые модель читает как данные, перехватывают управление приложением. Среди описанных последствий — утечка данных через сформированные агентом ссылки и запросы. InjecAgent [89] (Findings of ACL 2024) и AgentDojo [90] (NeurIPS 2024) — бенчмарки таких атак на агентов с инструментами. AgentDojo содержит 97 реалистичных задач и 629 сценариев атак; современные модели проваливают многие задачи даже без атак, а существующие атаки нарушают часть свойств безопасности.

ToolEmu [91] (ICLR 2024) эмулирует инструменты языковой моделью, чтобы находить рискованное поведение агентов без реального ущерба. RedCode [92] (NeurIPS 2024) — бенчмарк рискованного исполнения и генерации кода: 4050 тестовых случаев на Python и Bash по 25 типам критических уязвимостей. Агенты охотнее отказываются от явно опасных операций с ОС, но хуже распознают технически дефектный код. Более способные модели при запросе генерируют более изощрённый вредоносный код.

Защиты на уровне архитектуры дают гарантии, недостижимые обучением модели. CaMeL [93] разделяет поток управления, заданный доверенным запросом, и поток данных из недоверенных источников и применяет политики возможностей к вызовам инструментов. В AgentDojo он решил 77% задач с доказуемой защитой против 84% у незащищённой системы. Beurer-Kellner и соавт. [94] систематизировали шаблоны проектирования агентов, устойчивых к инъекциям: выбор действия из фиксированного набора, «план, затем исполнение», map-reduce с изолированной обработкой, двойная LLM, «код, затем исполнение», минимизация контекста.

Изоляция исполнения кода относится к системной части. Firecracker [96] (NSDI 2020) — микровиртуальные машины с малыми накладными расходами для недоверенного кода. Anjali и соавт. [95] (VEE 2020) сравнили Firecracker и gVisor с обычными контейнерами. Изоляция сильнее, чем у контейнера, но стоит производительности, прежде всего на сетевых и файловых операциях.

**Вывод для проекта:** на способность модели распознать атаку или опасный код полагаться нельзя. Безопасность обеспечивается архитектурой: изоляцией исполнения, отслеживанием происхождения данных, ограничением действий после чтения недоверенного контента и подтверждением пользователя.

## 2. Техническое задание

### 2.1. Аннотация и допущения

Документ описывает проект системы вопросно-ответного поиска и агентного анализа над приватным архивом исследовательских файлов: исходного кода Python, Jupyter-ноутбуков, PDF-документов и изображений. Такая система объединяет задачи обработки естественного языка (плотный и гибридный поиск, генерация с опорой на извлечённые фрагменты, text-to-SQL, дообучение моделей), компьютерного зрения (анализ вёрстки документов, OCR, классификация и описание изображений, визуальный поиск) и MLOps (калиброванный мониторинг деградации компонентов в эксплуатации).

**Допущения, требующие уточнения.** Объём корпуса принят равным 10³–10⁴ файлов, вычислительный ресурс — одна потребительская GPU с 16–24 ГБ памяти, язык материалов — смешанный русский и английский. При изменении этих параметров меняются выбор моделей и часть архитектурных решений, но не структура проекта.

Часть 2 продолжает Часть 1. В Части 1 описана система, которая отвечает на вопросы по приватному архиву .py, .ipynb, .pdf и .png со ссылками на источники. Система там только читает корпус.

Часть 2 превращает её из справочной системы в рабочего ассистента. Добавляются пять возможностей:

- обработка текстовых форматов DOCX и TXT;
- режим рассуждений (думающий режим) с управляемым бюджетом;
- загрузка файлов через пользовательский интерфейс;
- написание и исполнение кода с изолированным доступом к рабочей папке, по образцу код-агентов;
- поиск и чтение страниц в интернете.

Нумерация сквозная: проблемы продолжаются с P13, решения с S13, гипотезы с H10, функциональные требования с FR10, этапы с Э11.

**Главный вывод анализа.** Каждая из пяти возможностей по отдельности хорошо изучена. Основной риск создаёт их сочетание. Приватный корпус, недоверенный контент (веб-страницы и загруженные файлы), исполнение кода и сетевой доступ вместе образуют канал утечки данных через инъекции в промпт. Поэтому центральный элемент Части 2 — не новые инструменты, а слой политик доступа (S20), через который проходят все действия агента.

**Допущения** те же, что в Части 1: корпус 10³–10⁴ файлов, одна GPU на 16–24 ГБ, смешанный русский и английский языки, полностью локальный инференс для приватных данных.

### 2.2. Постановка проблемы

#### 2.2.1. Контекст и мотивация

За годы учёбы и работы у исследователя или ML-инженера накапливается разнородный архив: скрипты и модули, ноутбуки с экспериментами, статьи и отчёты, выгрузки графиков, схемы и скриншоты. Знание в таком архиве распределено по модальностям. Итоговая метрика эксперимента лежит в выводе ячейки ноутбука, её интерпретация — в соседней markdown-ячейке, описание метода — в PDF-статье, а сравнительный график сохранён отдельным PNG-файлом.

Поиск по именам файлов и полнотекстовый grep эту задачу не решают. Вопросы формулируются на естественном языке («в каком эксперименте был лучший ROC-AUC и что там отличалось?») и требуют связывания фактов из разных файлов и модальностей. Классическая схема генерации с извлечением (Retrieval-Augmented Generation, RAG) [1, 2] в текстовом варианте теряет структуру кода, игнорирует визуальную информацию и не умеет отвечать на агрегатные вопросы. Это и мотивирует проект мультимодальной агентной системы.

Система из Части 1 отвечает на вопросы, но не помогает работать. На практике после ответа почти всегда следует действие: пересчитать метрики по всем ноутбукам, исправить ошибку в модуле, построить сводный график, свериться с актуальной документацией библиотеки или со свежими статьями. Сейчас пользователь делает это вручную вне системы и теряет контекст.

Кроме того, в реальном архиве почти всегда есть DOCX и TXT: отчёты, заметки, черновики статей, логи обучения, выгрузки. Часть 1 их не покрывает. Наконец, работа с новым документом не должна требовать его добавления в постоянный корпус: нужен сценарий «загрузил файл — спросил — забыл».

#### 2.2.2. Характеристика корпуса

| Тип | Содержание | Специфика извлечения | Модальность |
|---|---|---|---|
| .py | Модули, функции, классы, скрипты обучения и препроцессинга | Синтаксическая структура (AST), импорты, граф вызовов. Идентификаторы требуют точного, а не только семантического поиска | Код |
| .ipynb | JSON: markdown-ячейки, код, выводы (текст, таблицы, изображения в base64), метаданные | Нелинейный порядок исполнения, связь «код → вывод», сильное раздувание объёма за счёт base64-графики | Код, текст, изображения |
| .pdf | Статьи, отчёты, конспекты, возможно сканы | Многоколоночная вёрстка, таблицы, формулы, рисунки, порядок чтения; для сканов нужен OCR | Текст, вёрстка, изображения |
| .png | Графики, схемы архитектур, скриншоты, фото и сканы | Информация только визуальная; способ обработки зависит от типа изображения | Изображения |

#### 2.2.3. Новые возможности

| Возможность | Что получает пользователь | Пример |
|---|---|---|
| DOCX и TXT | Отчёты, заметки, черновики и логи становятся частью корпуса наравне с кодом и PDF | «Что я писал в отчёте за март про переобучение?» |
| Режим рассуждений | На сложных вопросах модель сначала рассуждает, затем отвечает; переключатель и автоматический режим | «Почему модель в эксперименте X переобучилась, судя по кривым и коду?» |
| Загрузка файлов | Файл из интерфейса доступен в текущей сессии без добавления в корпус; по желанию его можно добавить | «Вот чужой ноутбук, сравни с моим подходом» |
| Код-агент | Агент пишет код, запускает его в песочнице, читает ошибки, исправляет и показывает изменения на подтверждение | «Пересчитай F1 во всех ноутбуках и сведи в таблицу» |

#### 2.2.4. Цель и задачи

**Цель:** разработать систему, которая отвечает на вопросы на естественном языке по приватному гетерогенному корпусу со ссылками на конкретные источники (файл, строка, ячейка, страница), поддерживает фактологические, навигационные, агрегатные и визуальные вопросы, работает полностью локально, отслеживает собственную деградацию в эксплуатации и воспроизводимо разворачивается на публичном демо-корпусе.

Для достижения цели решаются следующие задачи:

- **Ingestion.** Построить конвейер разбора файлов с отдельным обработчиком для каждого типа и единой моделью данных.
- **Индексация.** Построить гибридный поисковый индекс, реляционный каталог метаданных и граф связей между фрагментами.
- **Агент.** Реализовать агента с набором инструментов: поиск, SQL-запросы, навигация по файлам, анализ изображений.
- **Адаптация моделей.** Дообучить эмбеддер поиска, классификатор изображений и, опционально, детектор вёрстки и LLM для извлечения метаданных.
- **Оценка.** Разработать методологию оценки и эталонный набор вопросов, провести абляционные эксперименты.
- **Промышленная обвязка.** Обеспечить API, контейнеризацию, наблюдаемость и инкрементальную переиндексацию.
- **Мониторинг.** Обнаруживать деградацию компонентов в эксплуатации с контролируемой долей ложных тревог и запускать корректирующие действия.
- **Публикация.** Опубликовать код в открытом репозитории без раскрытия приватных данных.

**Цель:** расширить систему из Части 1 до рабочего ассистента, который читает текстовые форматы, рассуждает по запросу, работает с загруженными файлами, пишет и исполняет код в изолированной среде и пользуется интернетом. При этом сохраняются приватность корпуса, проверяемость ответов и управляемость действий.

Задачи:

- **Форматы.** Добавить обработчики DOCX и TXT в конвейер ingestion с сохранением структуры документа.
- **Рассуждения.** Реализовать режим рассуждений с тремя состояниями (выключен, включён, авто) и ограничением бюджета.
- **Загрузка.** Реализовать загрузку файлов в интерфейсе с сессионной областью видимости и явным добавлением в корпус.
- **Код-агент.** Реализовать цикл «план → правка → исполнение → исправление» в изолированной песочнице с показом изменений и подтверждением.
- **Интернет.** Реализовать инструменты поиска и чтения страниц с цитированием и разрешением конфликтов между источниками.
- **Безопасность.** Построить слой политик доступа, который предотвращает утечку приватных данных и разрушительные действия.
- **Оценка.** Расширить эталонный набор и методологию оценки на новые классы задач, включая атаки.

#### 2.2.5. Типология пользовательских запросов

Архитектура определяется классами вопросов, которые система должна обслуживать. Выделено шесть классов, каждый из которых задействует свой набор компонентов:

К классам Q1–Q6 из Части 1 добавляются пять новых.

| Класс | Пример | Необходимые компоненты |
|---|---|---|
| Q1. Фактологический | «Какой learning rate использовался в эксперименте с аугментациями?» | Гибридный поиск, реранкинг, генерация с цитированием |
| Q2. Навигационный по коду | «Где реализована функция подсчёта F1 и где она вызывается?» | AST-индекс, точный поиск идентификаторов, граф вызовов |
| Q3. Агрегатный и сравнительный | «В каком ноутбуке лучший ROC-AUC на задаче X?» | Реляционный каталог, text-to-SQL |
| Q4. Визуальный | «Найди схему архитектуры с блоком attention и объясни её» | Классификатор изображений, VLM, визуальный поиск |
| Q5. Многошаговый | «Сравни метод из статьи Y с моей реализацией в модуле Z» | Агент, несколько инструментов, планирование |
| Q6. Неотвечаемый | Вопрос, ответа на который в корпусе нет | Оценка релевантности найденного, корректный отказ |
| Q7. По загруженному файлу | «Что в этом договоре сказано про сроки сдачи?» | Загрузка, разбор, маршрутизация «весь файл в контекст или временный индекс» |
| Q8. Требующий рассуждения | «Почему метрика упала после смены препроцессинга? Сопоставь код и графики» | Режим рассуждений, несколько инструментов |
| Q9. Задача на код | «Напиши скрипт, который соберёт метрики из всех ноутбуков в CSV»; «Исправь ошибку в train.py» | Код-агент, песочница, показ изменений |
| Q10. Актуальная внешняя информация | «Какая сейчас последняя версия библиотеки X и что изменилось?» | Поиск в интернете, чтение страниц, цитирование URL |
| Q11. Смешанный: корпус и интернет | «Сравни мой метод с недавними статьями по теме» | Поиск по корпусу, интернет, рассуждение, разрешение конфликтов |

#### 2.2.6. Ограничения и допущения

- **Приватность.** Данные не покидают локальную машину, все модели исполняются локально. Внешние API допустимы только для публичного демо-корпуса.
- **Вычислительные ресурсы.** Одна GPU на 16–24 ГБ. Отсюда LLM класса 7–8 млрд параметров в 4-битной квантизации и дообучение методом QLoRA.
- **Объём корпуса.** Порядка 10³–10⁴ файлов. Это позволяет хранить индекс на одной машине, но делает ручную разметку всего корпуса невозможной.
- **Язык.** Смешанный русский и английский, поэтому нужны мультиязычные модели.
- **Трафик.** Система однопользовательская: органических запросов мало, а меток правильности в эксплуатации нет.
- **Публикация.** Код открыт. Приватные данные, производные от них индексы и веса, дообученные на них, не публикуются.
- **Приватность.** Содержимое корпуса и загруженных файлов не отправляется во внешние сервисы. Исключение — поисковые запросы в интернет, и к ним применяются отдельные правила (S20).
- **Права на запись.** Агент никогда не пишет напрямую в папку корпуса. Все изменения делаются в рабочей копии и применяются только после подтверждения пользователя.
- **Сеть.** Из песочницы сети по умолчанию нет. Доступ в интернет есть только у отдельного шлюза с инструментами поиска и чтения страниц.
- **Вычислительные ресурсы.** Одна GPU. Режим рассуждений и код-агент увеличивают число генерируемых токенов, поэтому бюджеты обязательны.
- **Пользователь.** Система однопользовательская; пользователь присутствует и может подтверждать действия.

### 2.3. Существующие проблемы применительно к кейсу

Ниже перечислены проблемы, которые возникают при построении системы именно над описанным корпусом. Для каждой указаны суть, конкретное проявление и основание в литературе.

#### P1. Потеря структуры при конвертации PDF

**Суть.** Конвертация PDF в текст разрушает многоколоночную вёрстку, порядок чтения, таблицы и формулы, смешивает подписи к рисункам с основным текстом. Сканы без текстового слоя дают пустой результат.

**Проявление в корпусе.** Научные статьи в двух колонках, таблицы результатов, конспекты-сканы. Ответы на вопросы о числах из таблиц становятся ненадёжными.

**Основание:** [17, 18, 19].

#### P2. Разрушение семантических единиц кода

**Суть.** Фиксированный чанкинг режет функции и классы посередине или склеивает несвязанные фрагменты. Эмбеддинг такого фрагмента плохо отражает его смысл.

**Проявление в корпусе.** Длинные модули обучения, классы моделей на сотни строк. Вопросы класса Q2 находят обрывки кода.

**Основание:** [13, 14].

#### P3. Ноутбук как нелинейный граф с выводами

**Суть.** Ячейки исполняются не по порядку, переменные передаются между ячейками неявно, выводы (метрики, таблицы, графики) отделены от породившего их кода. Изображения в base64 многократно раздувают объём. LLM не справляется с длинными ноутбуками целиком.

**Проявление в корпусе.** Результаты экспериментов живут именно в выводах. Без связи «код → вывод» на вопрос «какой скор дала эта модель» ответить нельзя.

**Основание:** [15, 16].

#### P4. Визуальная информация недоступна текстовому индексу

**Суть.** Графики, схемы и скриншоты не имеют текстового представления, а OCR извлекает лишь подписи осей и отдельные слова.

**Проявление в корпусе.** Схемы архитектур, кривые обучения, confusion matrix. Вопросы класса Q4 не решаются вовсе.

**Основание:** [20, 21, 22, 23].

#### P5. Лексико-семантический разрыв

**Суть.** Пользователь спрашивает на естественном языке, а в коде — идентификаторы (compute_f1, train_loop_v2) и аббревиатуры. Плотные модели плохо обобщаются вне домена и слабы на точных совпадениях. Корпус к тому же смешанно-языковой.

**Проявление в корпусе.** Вопрос «функция подсчёта F1» должен находить calc_metrics, а запрос по имени класса — точное вхождение.

**Основание:** [5, 6].

#### P6. Агрегатные вопросы вне возможностей поиска

**Суть.** Поиск возвращает k фрагментов и не может посчитать, сравнить или отсортировать по всему корпусу.

**Проявление в корпусе.** «Лучший эксперимент», «сколько ноутбуков используют XGBoost», «все запуски на датасете X». Вопросы класса Q3.

**Основание:** [25, 26].

#### P7. Ненадёжность агента

**Суть.** Неверный выбор инструмента, зацикливание, накопление ошибок по шагам, рост латентности и стоимости. Малые локальные LLM особенно склонны к ошибкам в формате вызовов инструментов.

**Проявление в корпусе.** 7–8-миллиардная локальная модель в роли оркестратора; вопросы класса Q5.

**Основание:** [27, 29, 30].

#### P8. Галлюцинации и неверная атрибуция

**Суть.** Модель отвечает из параметрической памяти вместо контекста, приписывает факт не тому файлу, игнорирует фрагменты в середине длинного контекста.

**Проявление в корпусе.** Особенно опасно для чисел: метрик и гиперпараметров. Ответ с неверной ссылкой хуже отказа.

**Основание:** [36, 38, 34].

#### P9. Отсутствие размеченных данных

**Суть.** Для приватного корпуса нет ни эталонных вопросов для оценки, ни пар для обучения эмбеддера. Ручная разметка дорогая.

**Проявление в корпусе.** Без эталонного набора невозможно доказать эффект любого улучшения.

**Основание:** [35, 36, 37].

#### P10. Безопасность и приватность

**Суть.** Инструкции внутри файлов (например, в markdown скачанного ноутбука) могут перехватить управление агентом. Возможны извлечение содержимого базы, запоминание данных дообученными моделями и утечка через публичный репозиторий (outputs ноутбуков, логи, ключи).

**Проявление в корпусе.** Агент с инструментами чтения файлов и исполнения кода. Код публикуется на GitHub.

**Основание:** [39, 40, 41, 42, 43].

#### P11. Эволюция корпуса и стоимость переиндексации

**Суть.** Файлы изменяются и добавляются, а полная переиндексация с OCR и VLM дорога.

**Проявление в корпусе.** Живой рабочий архив; VLM-описание одного изображения стоит секунды GPU-времени.

**Основание:** Инженерная проблема.

#### P12. Деградация компонентов в эксплуатации и ложные тревоги мониторинга

**Суть.** Компоненты деградируют со временем: корпус смещается (новые темы и типы файлов), обновляются модели, зависимости и параметры квантизации. Меток в эксплуатации нет, а органический трафик однопользовательской системы мал. Если мониторить два десятка метрик с порогами по умолчанию, получается лавина ложных тревог и лишних переобучений; без мониторинга деградация проходит незаметно.

**Проявление в корпусе.** 15–25 рядов вида «компонент × сегмент»: поиск по каждому типу файлов, реранкер, OCR, вёрстка, классификатор изображений, SQL, генерация по классам запросов. Общие зависимости (один эмбеддер, одна LLM) вызывают одновременную просадку многих рядов.

**Основание:** [44–55].

Проблемы P1–P12 описаны в Части 1. Ниже — новые проблемы, возникающие при расширении функциональности.

#### P13. Скрытая структура DOCX

**Суть.** DOCX — ZIP-архив с XML. Заголовки задаются стилями, нумерация списков — отдельной частью архива, таблицы могут быть вложенными. Комментарии, исправления (удалённый и вставленный текст), колонтитулы, сноски и встроенные изображения хранятся в разных местах. Наивное извлечение текста теряет иерархию разделов, смешивает удалённый текст с действующим и теряет таблицы и рисунки. Старый формат .doc вообще не является XML.

**Проявление в кейсе.** Отчёты и черновики статей с правками, таблицы результатов, вставленные графики.

**Основание:** [56, 57].

#### P14. Отсутствие структуры и разнородность TXT

**Суть.** Неизвестная кодировка (UTF-8, Windows-1251 и другие), отсутствие разметки, разное содержимое под одним расширением: заметки, markdown без расширения .md, логи обучения, табличные выгрузки, очень длинные файлы.

**Проявление в кейсе.** Логи с тысячами строк метрик по эпохам, заметки в кодировке Windows-1251, выгрузки из консоли.

**Основание:** [11, 58, 59].

#### P15. Цена и достоверность рассуждений

**Суть.** Рассуждение многократно увеличивает число токенов и задержку, особенно на локальной модели. На простых вопросах оно не улучшает ответ. Текст рассуждения выглядит как объяснение, но может не отражать реальные причины ответа, и пользователь склонен ему доверять.

**Проявление в кейсе.** Модель 7–8 млрд параметров на одной GPU; вопросы Q1 не требуют рассуждений, а Q5 и Q8 требуют.

**Основание:** [62, 66–68].

#### P16. Жизненный цикл и объём загружаемых файлов

**Суть.** Загруженный файл нужен в текущем разговоре, но не обязательно в корпусе. Файл может не поместиться в контекст, может дублировать файл корпуса, может содержать инъекцию или быть вредоносным архивом (DOCX — это ZIP). Неясно, сколько хранить файл и его индекс.

**Проявление в кейсе.** Чужие ноутбуки, статьи, договоры, выгрузки размером от килобайт до сотен мегабайт.

**Основание:** [38, 41, 70, 71].

#### P17. Надёжность генерации и правки кода

**Суть.** Код может запускаться, но решать не ту задачу. Правки ломают файлы (неверные номера строк, нарушенные отступы). Агент зацикливается на исправлениях. Малые локальные модели заметно слабее на задачах уровня SWE-bench.

**Проявление в кейсе.** Скрипты анализа по многим ноутбукам, исправление модулей, построение графиков.

**Основание:** [72–74, 76, 77].

#### P18. Изоляция исполнения и права доступа

**Суть.** Исполняемый код может удалить или испортить файлы корпуса, вывести данные наружу по сети, исчерпать ресурсы машины, установить вредоносный пакет или выйти за пределы контейнера. Модель плохо распознаёт рискованный код.

**Проявление в кейсе.** Код пишет модель, которая читала недоверенные веб-страницы и загруженные файлы.

**Основание:** [92, 95, 96].

#### P19. Качество, актуальность и противоречивость веб-источников

**Суть.** Найденные страницы бывают устаревшими, поверхностными или SEO-мусором. Ответы с веб-цитатами часто не подкреплены ими. Сведения из интернета могут противоречить корпусу. Лишний поиск ухудшает ответы на вопросы, которые решаются по корпусу.

**Проявление в кейсе.** Вопросы Q10 и Q11; сравнение своей работы со статьями.

**Основание:** [82, 83, 86–88].

#### P20. Утечка приватных данных через интернет и инъекции

**Суть.** Появляется канал наружу. Утечь можно тремя путями. Первый — сам поисковый запрос: если он составлен из содержимого корпуса, приватный текст уходит внешнему поисковику. Второй — инъекция на веб-странице или в загруженном файле, которая заставляет агента вставить приватные данные в URL запроса. Третий — сетевой запрос из песочницы или ссылка на изображение в ответе, которую отрисует интерфейс.

**Проявление в кейсе.** Приватный корпус + недоверенный контент + сетевые инструменты в одном агенте.

**Основание:** [41, 89, 90, 93, 94].

#### P21. Рост сложности оркестрации

**Суть.** Число инструментов и режимов растёт. Модель чаще ошибается в выборе инструмента, растут задержка и расход контекста, а пользователь теряет понимание, что агент делает и с какими правами.

**Проявление в кейсе.** Одна локальная модель управляет поиском, SQL, песочницей, интернетом и загрузками.

**Основание:** [69, 73, 90].

### 2.4. Теоретические решения для кейса

#### 2.4.1. Целевая архитектура

Система строится из пяти слоёв. Каждый слой заменяем и оценивается отдельно, что соответствует модульной парадигме RAG [2].

| Слой | Назначение и компоненты | Кандидатные технологии |
|---|---|---|
| 1. Ingestion | Роутер по типу файла; обработчики .py, .ipynb, .pdf, .png; извлечение метаданных; очередь задач | ast, tree-sitter, nbformat, Docling, OCR (PaddleOCR / Surya), VLM (Qwen2.5-VL) |
| 2. Представление | Единая модель «узел + связи»; текстовые и визуальные представления узла | Pydantic-схемы |
| 3. Хранилище | Гибридный векторный индекс; реляционный каталог; граф связей; исходные файлы и кэш | Qdrant, PostgreSQL или SQLite, файловая система |
| 4. Агент | Оркестратор ReAct; инструменты; проверка релевантности; генерация с цитированием | LangGraph, vLLM или Ollama, LLM 7–8B |
| 5. Сервинг и наблюдаемость | API, UI, трассировка, инкрементальная индексация, канареечные прогоны и калиброванный мониторинг деградации | FastAPI, Docker Compose, Langfuse, Streamlit или Gradio, driftfdr |

**Единая модель данных.** Все обработчики приводят содержимое к узлам. Узел имеет идентификатор, путь к файлу, тип файла и тип узла (функция, класс, markdown-ячейка, ячейка кода, вывод ячейки, раздел PDF, таблица, рисунок, изображение), ссылку на родителя, текстовое представление, ссылку на визуальное представление, метаданные и контент-хэш.

Между узлами хранятся типизированные связи:

- «содержит» — файл → ячейка, класс → метод;
- «вызывает» и «импортирует» — функция → функция, модуль → модуль;
- «порождает» — ячейка кода → её вывод;
- «иллюстрирует» — рисунок → раздел;
- «использует переменную» — ячейка → ячейка.

Такое представление позволяет агенту переходить от найденного фрагмента к его контексту, например от метрики к коду, который её посчитал.

Пятислойная архитектура Части 1 сохраняется. Добавляются новые компоненты, и все действия агента теперь проходят через слой политик.

| Компонент | Назначение | Кандидатные технологии |
|---|---|---|
| Обработчики DOCX и TXT | Новые ветки роутера ingestion; перевод в модель узлов Части 1 | Docling, python-docx, charset-normalizer, LibreOffice headless для .doc |
| Контроллер рассуждений | Режимы «выкл / вкл / авто», бюджет, классификатор сложности | Модель с гибридными режимами класса Qwen3, budget forcing в сервере инференса |
| Сервис загрузок | Приём, проверка, разбор, временный индекс сессии, срок хранения | FastAPI, отдельная коллекция Qdrant с TTL |
| Среда исполнения кода | Песочница с рабочей копией, исполнение Python и команд, тесты, ноутбуки | Docker + gVisor или микро-ВМ Firecracker, Jupyter kernel внутри |
| Веб-шлюз | Поиск, загрузка страниц, извлечение текста, кэш, фильтрация доменов | Самостоятельно размещённый метапоиск или поисковый API, trafilatura |
| Слой политик | Уровни доверия данных, отслеживание происхождения, правила для действий, подтверждения | Собственная реализация по схемам CaMeL и [94] |

Набор инструментов агента после расширения:

| Инструмент | Действие | Подтверждение | Доверие к результату |
|---|---|---|---|
| search, exact_search, sql_query, read_file, describe_image | Чтение корпуса (Часть 1) | Нет | Приватные данные |
| read_upload | Чтение загруженного файла | Нет | Недоверенные данные |
| run_code | Исполнение Python или команды в песочнице без сети | Нет, в пределах лимитов | По происхождению входных данных |
| view_file, edit_file, create_file | Просмотр и правка файлов рабочей копии | Нет | — |
| apply_changes | Перенос изменений из рабочей копии в папку пользователя | Да, всегда | — |
| web_search | Поисковый запрос во внешний поисковик | Да, если в запросе есть приватные сущности | Недоверенные данные |
| fetch_page | Загрузка страницы по URL из результатов поиска или от пользователя | Нет; иной URL — да | Недоверенные данные |
| install_package | Установка пакета в песочницу через зеркало | Да | — |

#### 2.4.2. Решения по проблемам

##### S1. Структурный разбор PDF (→ P1)

- Бейзлайн — конвейер Docling [18]: детекция вёрстки моделью, обученной на DocLayNet [17], и восстановление структуры таблиц. Документ превращается в иерархию разделов, а чанкинг идёт по этой иерархии, а не по символам (с учётом вывода [11]).
- Таблицы сохраняются как Markdown внутри раздела и отдельными узлами. Рисунки вырезаются и направляются в конвейер изображений (S4) со связью «иллюстрирует».
- OCR запускается только для страниц без текстового слоя: это определяется по доле извлекаемых символов, что экономит ресурсы.
- **CV-компонент проекта.** Дообучить собственный детектор вёрстки (например, семейства YOLO или RT-DETR) на DocLayNet и сравнить с моделью Docling по mAP на отложенной выборке и по качеству итогового поиска. Это полный CV-цикл: данные, обучение, оценка, экспорт в ONNX, инференс.

##### S2. AST-чанкинг кода с многоракурсным представлением (→ P2)

- Код разбирается в AST (модуль ast или tree-sitter). Единицы — функции и классы: крупные рекурсивно делятся по дочерним узлам, мелкие соседние объединяются до лимита, как в cAST [13].
- Каждому фрагменту добавляется контекстный заголовок: путь к файлу, имя класса, сигнатура, докстринг. Опционально — краткое описание на естественном языке, сгенерированное LLM. Это реализует многоракурсное представление, на перспективность которого указывают авторы cAST, и сокращает разрыв P5.
- Статически извлекаются импорты и вызовы и записываются в граф связей. Это даёт ответы класса Q2 («где вызывается») без LLM.

##### S3. Ноутбук как граф ячеек (→ P3)

- Разбор через nbformat: каждая ячейка — узел. Выводы отделяются: текстовые усекаются с сохранением хвоста (где обычно итоговые метрики), изображения декодируются из base64 в файлы и уходят в конвейер S4. Связь «порождает» сохраняется.
- Статический анализ определений и использований переменных между ячейками строит граф зависимостей. Неоднозначности разрешаются LLM локально, по одной ячейке, — по схеме CRABS [15], которая избегает провала на длинных ноутбуках.
- Иерархические суммаризации (ячейка → логический блок → ноутбук), по аналогии с RAPTOR [12], обслуживают вопросы уровня «о чём этот эксперимент».
- LLM со структурированным выводом (JSON-схема) извлекает метаданные эксперимента — модель, датасет, метрики со значениями, ключевые гиперпараметры — в реляционный каталог (S6). Каждое значение хранит ссылку на ячейку-источник.

##### S4. Конвейер изображений и визуальный индекс (→ P4)

- **Ступень 1: классификация типа изображения** (график, схема или диаграмма, скриншот, фото, скан документа). Небольшая модель из timm дообучается на нескольких сотнях размеченных изображений. Это второй самостоятельный CV-компонент: разметка, аугментации, метрики, анализ ошибок.
- **Ступень 2: обработка по типу.** Для скриншотов и сканов — OCR. Для графиков — перевод в таблицу по схеме DePlot [23] плюс описание осей и тренда VLM. Для схем — описание VLM с перечислением блоков и связей. Все текстовые представления индексируются как обычные узлы.
- **Параллельный визуальный индекс.** Мультивекторные эмбеддинги изображений в стиле ColPali [20] для страниц PDF и изображений.
- **Эксперимент.** Сравнить на вопросах класса Q4 три варианта: только «текст из изображения», только визуальный индекс и их слияние через RRF. Гипотеза — по результатам VisRAG [21] — визуальный индекс выигрывает на насыщенных графикой документах.

##### S5. Гибридный поиск с переранжированием (→ P5)

- Основной поисковик — BGE-M3 [6] в плотном и разреженном режимах. Слияние результатов — через RRF [9], переранжирование top-50 кросс-энкодером [8] до top-5–10.
- Отдельный инструмент точного поиска (grep по регулярному выражению и индекс идентификаторов) — для запросов с именами функций, классов и файлов. Решение об его использовании принимает агент.
- Для коротких и абстрактных запросов — переформулирование в стиле HyDE [10].
- Дообучение эмбеддера на синтетических парах из собственного корпуса (S9) по схеме Promptagator [35] — с контрастивной функцией потерь и трудными негативами из того же файла.

##### S6. Реляционный каталог и text-to-SQL (→ P6)

- Схема каталога: files, notebooks, cells, experiments, metrics, hyperparameters, functions, images, relations. Каталог наполняется детерминированно (S2, S3) и LLM-извлечением со ссылкой на источник.
- SQL-инструмент агента строится по схеме CHESS [26]. Описания таблиц и колонок индексируются в векторном поиске. Характерные значения (названия моделей, датасетов) ищутся нечётко. В промпт подаётся суженная схема и несколько похожих примеров «вопрос–SQL» из пополняемой базы.
- Контур безопасности: пользователь БД только для чтения, валидация SQL разбором (например, sqlglot) до исполнения, запрет DDL и DML, принудительный LIMIT, таймаут. При ошибке исполнения или пустом результате — самокоррекция, не более двух–трёх попыток.

##### S7. Надёжный контур агента (→ P7)

- Маршрутизатор перед агентом: простые вопросы Q1 обслуживаются прямым RAG без агентного цикла. Это снижает латентность и число ошибок; в агентный ReAct-цикл [27] попадают только Q3–Q5.
- Малый фиксированный набор инструментов с JSON-схемами: search, exact_search, sql_query, read_file, list_dir, describe_image, опционально run_code. Для локальной модели — ограниченное декодирование (constrained decoding) по схеме вызова, что устраняет синтаксические ошибки вызовов.
- Оценщик релевантности найденного по схеме CRAG [29]: при низкой оценке — переформулирование запроса или смена инструмента, а после исчерпания попыток — честный отказ (класс Q6).
- Жёсткие лимиты: число шагов (например, 8), бюджет токенов, таймаут. Каждая траектория полностью логируется; неудачные траектории становятся материалом для улучшения промптов и примеров.

##### S8. Проверяемые ответы (→ P8)

- Каждое утверждение в ответе должно ссылаться на узел (файл и строка, ячейка, страница). Отсутствие ссылки означает отказ от утверждения. Системный промпт требует отвечать только по контексту и явно сообщать об отсутствии ответа.
- Число фрагментов в контексте ограничено (5–8); наиболее релевантные ставятся в начало и конец контекста с учётом эффекта «потери в середине» [38].
- Постпроверка: для числовых утверждений — сверка значения с текстом фрагмента-источника; для остальных — оценка верности контексту в духе RAGAS [36].
- Опционально — QLoRA-дообучение [33] генератора по схеме RAFT [34] на синтетических примерах с отвлекающими фрагментами: модель учится цитировать нужный фрагмент и игнорировать шум.

##### S9. Данные для оценки и обучения (→ P9)

- **Эталонный набор:** 100–150 вопросов, стратифицированных по классам Q1–Q6 и типам файлов, с эталонным ответом и эталонными узлами-источниками. Составляется вручную, это главный артефакт проекта.
- **Синтетика:** LLM генерирует вопросы к случайно выбранным узлам. Сохраняются только пары, прошедшие фильтр согласованности (сгенерированный вопрос находит свой узел в top-k), по аналогии с Promptagator [35].
- **Разделение данных:** синтетика для обучения, пул канареек для мониторинга (S12) и эталонный набор для оценки разделяются по файлам, чтобы исключить утечку.
- **Калибровка LLM-судьи:** согласие с ручной оценкой на 30–50 ответах; рандомизация порядка сравниваемых ответов; запрет судье оценивать ответы той же модели без контроля — с учётом смещений из [37].

##### S10. Модель угроз и защита (→ P10)

- Полностью локальный инференс для приватного корпуса.
- Содержимое файлов подаётся модели как данные в явных разделителях. Системный промпт запрещает исполнять инструкции из данных. Опасные действия (исполнение кода, запись) требуют подтверждения пользователя. Это меры против непрямых инъекций [41].
- Принцип наименьших привилегий: файловая система и БД только на чтение; run_code исполняется в контейнере без сети и с лимитами ресурсов.
- Веса, дообученные на приватном корпусе, не публикуются с учётом [43]. Публикуются только веса, обученные на демо-корпусе.
- Гигиена репозитория: pre-commit хуки (gitleaks, nbstripout), .gitignore для данных, индексов и логов, конфигурация через переменные окружения.

##### S11. Инкрементальная индексация (→ P11)

- Контент-хэш на уровне файла и узла: переиндексируются только изменённые узлы, связи пересчитываются локально.
- Кэш дорогих результатов (OCR, описания VLM, суммаризации) по хэшу входа: повторная обработка неизменённого изображения бесплатна.
- Очередь задач с приоритетами; версионирование схемы индекса и моделей эмбеддингов (смена эмбеддера требует полной переиндексации векторов, но не повторного разбора).

##### S12. Калиброванный мониторинг на канареечных запросах (→ P12)

- **Сигнал — ошибка компонентов, а не входные данные** [47, 48]. Источник сигнала — канареечные запросы: по расписанию прогоняется случайная подвыборка из пула синтетических вопросов с известными ответами. Пул порождается по схеме S9 и отделён от обучающей синтетики и эталонного набора. На каждом шаге фиксируются ошибки 0/1 по компонентам: промах поиска@5 по типу файла, промах реранкера, несовпадение результата SQL, неверный класс изображения, превышение порога CER, неверный ответ по оценке судьи.
- **Случайная подвыборка на каждом шаге обязательна.** При детерминированном конвейере (температура 0) фиксированный набор канареек даёт кусочно-постоянный ряд, и бутстреп-калибровка теряет смысл. Пул пополняется вопросами к новым файлам со стратификацией по давности файла; иначе мониторинг видит только старую часть корпуса.
- **Парк рядов.** 15–25 рядов вида «компонент × сегмент». Порог каждого детектора калибруется бутстрепом с учётом автокорреляции [54, 55]. Решение по парку принимается с поправкой Бонферрони в окне: она ограничивает вероятность хотя бы одной ложной тревоги при любой зависимости рядов. Процедура BH [49] — альтернатива, когда многие компоненты деградируют одновременно. Отклонение каждого ряда считается от медианы по парку, а сама медиана проверяется отдельно: её тревога означает событие всего парка — обновление эмбеддера, LLM, квантизации или индекса.
- **Нулевая гипотеза с допуском δ** [48]: тревога только при существенном росте ошибки. Допуск выводится из стоимости корректирующего действия на горизонте. Например, если дообучение эмбеддера занимает около часа GPU, переобучать выгодно лишь при ухудшении, которое за горизонт обходится дороже.
- **Действия по тревоге.** Для тревоги по компоненту — точечное действие: дообучение эмбеддера на свежих синтетических парах, обновление few-shot примеров SQL, дообучение классификатора изображений, переиндексация сегмента. Для тревоги парка — проверка и откат последнего изменения общей зависимости.
- **Онлайн-прокси без меток** — вспомогательные ряды: доля ошибок исполнения SQL, доля оценок «нерелевантно» у оценщика CRAG, доля отказов, отрицательные оценки пользователя. Прокси видят не все виды деградации, поэтому основным сигналом остаются канарейки.
- **Реализация.** Библиотека driftfdr (Apache-2.0, см. раздел «Программные инструменты»): потоковый монитор с поправкой на множественность, режимом выделения общей составляющей и сохранением состояния между перезапусками сервиса. Канарейки запускаются фоновой задачей в периоды простоя GPU; ориентировочный бюджет — 10–30 вопросов в час, уточняется по нагрузке.
- **Ограничения.** Библиотека проверена авторами на синтетике, открытых табличных наборах и курсах валют, но не на компонентах RAG-систем; перенос — предмет гипотезы H9. При бинарных ошибках и малых подвыборках обнаруживаются только существенные ухудшения, мелкие неотличимы от шума.

##### S13. Декларативный разбор DOCX (→ P13)

- Разбор без моделей зрения: чтение XML через Docling [56] или python-docx. Стили заголовков дают иерархию разделов, и чанкинг идёт по ней, как для PDF в Части 1.
- **Перевод в модель узлов Части 1.** Разделы, абзацы и таблицы становятся узлами. Таблицы сохраняются в Markdown и отдельными узлами. Встроенные изображения извлекаются и уходят в конвейер изображений (S4 Части 1) со связью «иллюстрирует».
- **Правки и комментарии.** По умолчанию индексируется текст с принятыми исправлениями. Удалённые фрагменты и комментарии — отдельные узлы с пометкой типа; они доступны по явному запросу («какие правки вносились в раздел 2?») и не смешиваются с действующим текстом.
- Колонтитулы и сноски — метаданные раздела. Свойства документа (автор, даты создания и изменения) уходят в реляционный каталог для агрегатных вопросов.
- Старый .doc конвертируется в DOCX через LibreOffice в режиме без интерфейса, затем разбирается общим путём.

##### S14. Классификация и сегментация TXT (→ P14)

- Определение кодировки по статистике байтов (charset-normalizer) с сохранением кодировки в метаданных. Нераспознанные файлы попадают в журнал ошибок, а не молча портятся.
- Эвристический классификатор типа содержимого: markdown-подобный текст, проза, лог, табличная выгрузка, код без расширения. Признаки: доля строк с временными метками, разделителями и символами разметки.
- **Обработка по типу.** Markdown-подобный текст режется по заголовкам. Проза — по абзацам, а при их отсутствии — сегментацией по смене темы в духе TextTiling [58]. Лог — по записям или временным окнам; числовые метрики из логов обучения извлекаются в каталог и связываются с ноутбуками. Табличные выгрузки загружаются в каталог как таблицы.
- Пропозиционная индексация [59] — только эксперимент на небольшом подмножестве прозы с учётом [11].

##### S15. Управляемый режим рассуждений (→ P15)

- **Одна модель с двумя режимами** класса Qwen3 [65]: не нужно держать в видеопамяти вторую модель.
- **Три состояния переключателя в интерфейсе.** «Выкл» — быстрый ответ. «Вкл» — рассуждение с бюджетом. «Авто» — решение принимает маршрутизатор.
- **Маршрутизатор режима** — небольшой классификатор по схеме Adaptive-RAG [69]. Признаки: класс запроса (Q1–Q11), число сущностей, наличие сравнений и причинных вопросов. Классы Q1 и Q7 обычно идут без рассуждения, Q5, Q8 и Q11 — с рассуждением. Дополнительно: эскалация, если оценщик релевантности (S7 Части 1) дал низкую уверенность или несколько быстрых ответов расходятся [61].
- **Бюджет** — жёсткий лимит токенов рассуждения с принудительным завершением (budget forcing [64]), зависящий от класса запроса. Это ограничивает передумывание [66] и задержку.
- **Рассуждение с инструментами.** Модель может вызывать поиск посреди рассуждения. Найденное сначала сжимается отдельным шагом анализа документов по схеме Search-o1 [84] и только затем попадает в цепочку.
- **Отображение.** Рассуждение показывается свёрнутым блоком с пометкой «черновик рассуждений». Итоговый ответ, как и в Части 1, подтверждается только ссылками на источники: по [67, 68] рассуждение не является объяснением. В историю диалога попадает только итоговый ответ, а не рассуждение, — это экономит контекст.

##### S16. Сервис загрузок с сессионной областью (→ P16)

- **Приём и проверка.** Тип определяется по сигнатуре файла, а не по расширению. Лимит размера. Защита от ZIP-бомб для DOCX и архивов: лимит распакованного объёма и числа файлов. Разбор идёт в изолированном процессе.
- **Область видимости.** По умолчанию файл доступен только в текущей сессии: временная коллекция индекса со сроком хранения. Добавление в постоянный корпус — явное действие пользователя, после которого файл проходит обычный конвейер. Дубликаты файлов корпуса распознаются по хэшу.
- **Маршрутизация.** Если разобранный файл укладывается в эффективный бюджет контекста (с запасом с учётом RULER [71], ориентировочно не более трети окна), он подаётся целиком. Иначе используется временный индекс и поиск. Переход между путями — по схеме Self-Route [70]: если модель сообщает, что найденного недостаточно, в контекст подаются более крупные фрагменты или весь файл по частям.
- **Недоверенность.** Содержимое загрузки помечается как недоверенное для слоя политик (S20).

##### S17. Код-агент с обратной связью от исполнения (→ P17)

- **Действия кодом** по схеме CodeAct [74]: агент пишет Python, который исполняется в песочнице. Результат, stdout, stderr и traceback возвращаются агенту.
- **Интерфейс агента** по схеме SWE-agent [73]: просмотр файла окнами с номерами строк, поиск по рабочей копии, правка заменой фрагмента с автоматической проверкой синтаксиса и линтером; некорректная правка отклоняется до записи.
- **Цикл:** план → правка в рабочей копии → запуск (скрипт, тесты, ноутбук) → анализ ошибок → исправление [77]. Не более N итераций (например, 5). Выводы из неудачных попыток сохраняются в рамках задачи [78].
- **Фиксированные конвейеры** для типовых задач по схеме Agentless [76]: «собрать метрики из ноутбуков», «построить график по логам», «исправить ошибку по traceback». Свободный агентный цикл — только для остального.
- **Контрольные точки.** Рабочая копия находится под git: каждый шаг — коммит, откат возможен в любой момент. Итог показывается пользователю как diff, а в его папку переносится только после подтверждения (apply_changes).
- **Замечание о модели.** Локальная модель 7–8 млрд параметров слаба на сложных задачах. Для кода допускается замена на специализированную кодовую модель того же размера или внешний API. Внешний API разрешён только для публичного кода и демо-корпуса.

##### S18. Изолированная среда исполнения (→ P18)

- **Уровень изоляции.** Контейнер с ядром-перехватчиком gVisor или микро-ВМ Firecracker [96]. Выбор — по результатам сравнения [95]: gVisor проще в развёртывании, Firecracker даёт более сильную изоляцию и дороже в эксплуатации.
- **Файловая система.** Папка корпуса монтируется только на чтение. Рабочая копия — отдельный том с правом записи. Секреты хоста, домашняя директория и сокет Docker недоступны.
- **Сеть** в песочнице отключена по умолчанию. Установка пакетов — только через локальное зеркало или белый список индекса пакетов и с подтверждением.
- **Ресурсы.** Лимиты CPU, памяти, времени исполнения, размера диска и числа процессов. Процесс работает без root, с фильтром системных вызовов. Песочница пересоздаётся для каждой задачи.
- **Принцип:** RedCode [92] показывает, что модели плохо распознают рискованный код, поэтому защита держится на изоляции, а не на суждении модели. Проверка кода моделью перед запуском — дополнительный, а не основной барьер.

##### S19. Веб-шлюз с проверкой и цитированием (→ P19)

- **Когда искать.** Маршрутизатор отправляет запрос в интернет при временных маркерах («последняя версия», «в этом году»), при низкой релевантности лучшего результата в корпусе и по явному включению переключателя «Интернет» пользователем. Это следует выводу [82] о вреде лишнего поиска.
- **Поиск и извлечение.** web_search возвращает список URL и сниппетов. fetch_page загружает страницу, извлекает основной текст и кэширует его. Приоритет — первичным источникам: официальной документации, arXiv, ACL Anthology, репозиториям. Известные агрегаторы и SEO-сайты понижаются.
- **Сжатие перед рассуждением.** Отдельный шаг извлекает из страниц только относящиеся к вопросу фрагменты [84]. В контекст попадает ограниченное число фрагментов в осмысленном порядке [83].
- **Цитирование** — URL и дата обращения у каждого утверждения. Постпроверка подкреплённости каждого предложения цитатой; неподкреплённые утверждения удаляются или помечаются [86].
- **Конфликты.** Сведения из корпуса и из интернета не смешиваются молча: ответ показывает обе версии с источниками и датами [87, 88].

##### S20. Слой политик и отслеживание происхождения данных (→ P20)

- **Уровни доверия:** доверенные данные (запрос пользователя), приватные (корпус и каталог), недоверенные (веб-страницы, загрузки, вывод кода, обработавшего недоверенные данные). Каждое значение в контексте агента несёт метку происхождения.
- **Правило 1. Поисковые запросы.** Запрос в интернет формируется из вопроса пользователя, а не из содержимого корпуса. Если в запросе обнаружены приватные сущности (имена файлов, фрагменты кода, названия внутренних проектов из каталога), запрос показывается пользователю на подтверждение или обезличивается.
- **Правило 2. Действия после недоверенного контента.** После того как в контекст попали недоверенные данные, действия с внешним эффектом — fetch_page по URL не из результатов поиска, apply_changes, install_package — требуют подтверждения. Это реализация шаблона «план, затем исполнение» [94]: план действий фиксируется до чтения недоверенных данных.
- **Правило 3. URL.** fetch_page принимает только URL из результатов поиска или от пользователя. URL, собранный моделью из данных, блокируется: это закрывает утечку через параметры запроса [41].
- **Правило 4. Интерфейс.** Ответ не подгружает внешние изображения и не делает ссылки активными автоматически, чтобы отрисовка ответа не отправила данные наружу.
- **Изоляция обработки.** Для сложных случаев недоверенный документ обрабатывается отдельным вызовом модели без инструментов, который возвращает структурированную выжимку. Это шаблон двойной LLM [94]; развитие этой идеи с формальными гарантиями — CaMeL [93].
- **Проверка** — красное тестирование по образцу AgentDojo [90] и InjecAgent [89] на собственных сценариях (S21, H16).

##### S21. Управляемая оркестрация и прозрачность (→ P21)

- **Наборы инструментов по режимам.** Режим вопросов — только инструменты чтения. Режим кода добавляет песочницу. Интернет добавляется переключателем. Меньше инструментов в контексте — меньше ошибок выбора.
- **Интерфейс.** Переключатели «Думать», «Интернет», «Код», кнопка загрузки файла. Панель трассировки показывает шаги агента, вызовы инструментов и метки доверия. Просмотр diff и диалоги подтверждения для действий из таблицы 5.
- **Лимиты Части 1** (число шагов, бюджет токенов, таймауты) расширяются на новые инструменты. Каждая траектория логируется.
- **Мониторинг.** В канареечные прогоны (S12 Части 1) добавляются ряды для новых компонентов: разбор DOCX и TXT, код-задачи с тестами. Интернет-инструменты в канарейки не входят, чтобы не зависеть от изменчивого внешнего контента.

| P21 Оркестрация | Инструменты по режимам, трассировка, лимиты | [69, 73] | Ошибки выбора инструмента; задержка |

| Q9 Задача на код | 15–25 | Постановка, исходное состояние рабочей копии и автоматические тесты, проверяющие результат |

#### 2.5.2. Метрики

- **Поиск:** Recall@k, MRR и nDCG@10 по эталонным узлам [5].
- **Генерация:** верность контексту и релевантность ответа [36]; корректность ответа по калиброванному LLM-судье [37]; точность цитирования — доля ссылок, действительно подтверждающих утверждение.
- **SQL:** точность исполнения — совпадение результатов, как в BIRD [25].
- **Агент:** доля успешно решённых задач, среднее число шагов, латентность p50 и p95, стоимость в токенах.
- **Компоненты CV:** mAP@[0,5:0,95] детектора вёрстки; accuracy и macro-F1 классификатора изображений; CER для OCR.
- **Отказы (Q6):** точность и полнота корректных отказов.
- **Мониторинг:** задержка обнаружения внесённой деградации, доля ложных тревог, событийные precision, recall и F1, число лишних корректирующих действий.
- **DOCX и TXT:** метрики поиска Части 1 по новым форматам; точность ответов по таблицам DOCX; доля файлов TXT с корректной кодировкой и типом.
- **Рассуждения:** точность по классам запросов в зависимости от числа токенов и задержки (кривая «качество — затраты»); доля запросов, где авторежим выбрал рассуждение; доля токенов, потраченных без прироста точности [66].
- **Загрузки:** точность Q7 по размерам файлов; доля запросов, ушедших в длинный контекст; средняя стоимость запроса.
- **Код:** доля задач, прошедших тесты; среднее число итераций; доля правок, отклонённых проверкой синтаксиса; доля diff, принятых пользователем.
- **Интернет:** точность Q10 и Q11; подкреплённость предложений цитатами и точность цитат по методике [86]; доля лишних обращений в интернет на вопросах, решаемых по корпусу.
- **Безопасность:** доля успешных атак и полезность под атакой по методике AgentDojo [90]; доля опасных код-задач, заблокированных песочницей или политиками.

#### 2.5.3. Гипотезы и абляции

| № | Гипотеза | Эксперимент |
|---|---|---|
| H1 | AST-чанкинг превосходит фиксированный на вопросах о коде | Recall@5 на Q2 и части Q1: построчный против AST-чанкинга, с контекстными заголовками и без |
| H2 | Гибридный поиск с реранкером превосходит чисто плотный | Абляция: плотный → + разреженный + RRF → + реранкер |
| H3 | Дообученный на синтетике эмбеддер превосходит базовый | Базовый BGE-M3 против дообученного на отложенных файлах |
| H4 | Визуальный индекс превосходит «текст из изображения» на Q4 | Три варианта из S4, включая слияние |
| H5 | SQL-инструмент решает Q3, недоступные RAG | Агент без SQL против агента с SQL |
| H6 | Проверка релевантности снижает долю неверных ответов | Агент с оценщиком CRAG и без него; доля корректных отказов на Q6 |
| H7 | RAFT-дообучение повышает верность контексту | Базовая LLM против QLoRA-RAFT |
| H8 | Собственный детектор вёрстки не хуже модели Docling на корпусе | mAP и влияние на Recall@5 по PDF-вопросам |
| H9 | Калиброванный мониторинг с поправкой на число рядов обнаруживает деградацию при меньшей доле ложных тревог, чем детекторы с порогами по умолчанию | Стенд с искусственной порчей в известные моменты: замена эмбеддера на более слабый, зашумление изображений перед OCR, удаление few-shot примеров SQL, добавление файлов нового домена. Сравнение с Page-Hinkley на порогах по умолчанию и с калибровкой без поправки |
| H10 | Декларативный разбор DOCX превосходит извлечение сплошного текста | Recall@5 и точность ответов по таблицам: сплошной текст против структурного разбора |
| H11 | Авторежим рассуждений близок по точности к «всегда вкл» при заметно меньшем числе токенов | Три режима на всех классах; кривая «точность — токены» [62, 66] |
| H12 | Self-Route для загрузок сопоставим по точности с подачей файла целиком при меньшей стоимости | Весь файл против временного индекса против Self-Route на трёх размерах [70] |
| H13 | Цикл исправления по результатам исполнения повышает долю решённых код-задач | Однократная генерация против цикла из N итераций [77] |
| H14 | Специализированные инструменты правки уменьшают число поломок по сравнению с правкой через оболочку | ACI против sed и перезаписи файла: доля испорченных файлов [73] |
| H15 | Адаптивный выход в интернет улучшает Q10 и не ухудшает Q1–Q6 | Без интернета против «всегда искать» против адаптивного маршрутизатора [82] |
| H16 | Слой политик снижает долю успешных атак почти до нуля при небольшой потере полезности | С политиками и без них на сценариях атак; сравнение с ориентиром CaMeL (77% против 84%) [93] |

Каждый эксперимент меняет ровно один компонент при фиксированных остальных. Результаты оформляются таблицей абляций: она нужна и для отчёта, и для README публичного репозитория (в агрегированном виде, без приватного содержимого).

### 2.8. Риски

| Риск | Вероятность | Меры снижения |
|---|---|---|
| Малая локальная LLM ненадёжна как оркестратор | Высокая | Маршрутизатор, ограниченное декодирование, узкий набор инструментов; в крайнем случае детерминированный граф вместо свободного агента |
| Нехватка видеопамяти для VLM и LLM одновременно | Средняя | Пакетная офлайн-обработка изображений при индексации, выгрузка моделей, квантизация |
| Эталонный набор мал и смещён | Средняя | Стратификация, доразметка по результатам анализа ошибок, доверительные интервалы через бутстрэп |
| LLM-судья систематически ошибается | Средняя | Калибровка на ручной выборке, рандомизация порядка, выборочная ручная проверка |
| Утечка приватных данных в публичный репозиторий | Низкая при соблюдении мер | pre-commit хуки, nbstripout, раздельные конфигурации, ревью истории перед публикацией |
| Разнородность корпуса выше ожидаемой (форматы, кодировки) | Средняя | Устойчивые обработчики с журналом ошибок, fallback на простую текстовую экстракцию |
| Канарейки нагружают GPU и конкурируют с запросами пользователя | Средняя | Прогон в простое, малые подвыборки, приоритет пользовательских запросов в очереди |
| Канареечные вопросы не отражают реальных запросов | Средняя | Пополнение пула по обезличенным логам реальных вопросов, стратификация по классам Q1–Q6 и давности файлов |
| Локальная модель слаба как код-агент | Высокая | Фиксированные конвейеры для типовых задач, специализированная кодовая модель, внешний API только для публичного кода |
| Рассуждения делают ответы слишком медленными | Средняя | Авторежим, бюджет с принудительным завершением, рассуждение только для Q5, Q8 и Q11 по умолчанию |
| Утечка приватных данных через поисковые запросы | Средняя | Правило 1 S20: запросы только из вопроса пользователя, обнаружение приватных сущностей, подтверждение |
| Новые виды инъекций обходят политики | Средняя | Защита архитектурой, а не фильтрами; регулярное пополнение сценариев атак; подтверждение всех действий с внешним эффектом |
| Выход за пределы песочницы | Низкая | gVisor или Firecracker, отсутствие сети и секретов, пересоздание среды на каждую задачу, обновления |
| Пользователь устаёт от подтверждений и нажимает «да» не глядя | Средняя | Подтверждения только для действий с внешним эффектом; понятное описание действия и diff; группировка подтверждений в рамках одного плана |
| Нехватка видеопамяти при одновременной работе LLM, VLM и кодовой модели | Средняя | Гибридная модель вместо двух, выгрузка неактивных моделей, очередь задач с приоритетами |
| Изменчивость интернета ломает воспроизводимость оценки | Высокая | Кэш страниц для эталонного набора, фиксированные снимки, отдельная оценка на живом интернете |
