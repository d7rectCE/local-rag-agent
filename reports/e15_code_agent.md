# Э15. Песочница и код-агент

Критерий приёмки (ТЗ ч.2): выполнены FR13, FR14 и NFR8, проверены H13 и H14.

- **FR13:** код-агент просматривает, правит и создаёт файлы в рабочей копии, исполняет код, тесты и ноутбуки в песочнице, показывает diff.
- **FR14:** изменения переносятся в папку пользователя только после подтверждения; можно откатиться к любой контрольной точке.
- **NFR8:** код исполняется только в песочнице без сети, без секретов хоста и без записи в папку корпуса.
- **H13:** цикл исправления по результатам исполнения повышает долю решённых задач (Chen и др., Self-Debug [24]).
- **H14:** специализированные инструменты правки (ACI, SWE-agent [20]) уменьшают число испорченных файлов по сравнению с перезаписью.

Все числа получены на публичном демо-корпусе и наборе [`evalsets/code_v1.yaml`](../evalsets/code_v1.yaml) (15 задач). Модель — `qwen3.5:9b`, песочница — образ `rag-sandbox:py312` ([`docker/sandbox.Dockerfile`](../docker/sandbox.Dockerfile), версии пакетов закреплены). Спецификация прогона — [`configs/ablations/e15.yaml`](../configs/ablations/e15.yaml), полные таблицы — [`reports/e15/`](e15).

## Что сделано

**Песочница (NFR8, NFR11).** Каждый запуск — отдельный контейнер `docker run --rm` со следующими ограничениями:

- `--network none`, `--read-only` для корневой системы, `/tmp` в памяти (256 МБ);
- пользователь `1000:1000`, `--cap-drop ALL`, `no-new-privileges`;
- лимиты памяти, CPU, процессов и времени берутся из конфига `code.*`: 2 ГБ, 2 CPU, 256 процессов, 120 с на запуск;
- на запись смонтирована только рабочая копия. Переменные окружения хоста в контейнер не передаются.

Папка корпуса по умолчанию не монтируется совсем: иначе стали бы видны папки, исключённые из индексации. Нужные текстовые файлы уже лежат в рабочей копии, и при её создании применяются те же исключения.

Тест [`test_docker_sandbox_isolation`](../tests/test_code_agent.py) проверяет в настоящем контейнере:

- сеть закрыта;
- uid = 1000;
- корень только для чтения;
- переменная-секрет хоста не видна;
- запись в рабочую копию работает;
- зависший процесс снимается по таймауту.

**Рабочая копия под git (FR13, FR14).** Задача получает копию текстовых файлов проекта в отдельном git-репозитории. Каждый шаг агента, изменивший файлы, фиксируется контрольной точкой. Результат показывается как diff:

- `apply_changes` переносит изменения в папку пользователя только по явному подтверждению (политика «всегда подтверждать»);
- `rollback` возвращает к любой контрольной точке.

Тест [`test_engine_code_task_applies_only_on_request`](../tests/test_code_agent.py) проверяет, что без подтверждения папка пользователя не меняется.

**ACI (SWE-agent [20]).** Инструменты правки:

- просмотр файла окном с номерами строк;
- поиск по рабочей копии;
- замена фрагмента, который встречается ровно один раз;
- создание файла.

Правка, после которой Python-файл или ноутбук перестаёт разбираться, не записывается: агент получает ошибку синтаксиса и строку. Для H14 есть базовый вариант `code.aci: false`: файл целиком перезаписывается без проверки.

**Цикл исправления (Self-Debug [24], Reflexion).** Агент чередует правки и запуски: скрипты, тесты, ноутбуки, фрагменты Python. Он получает stdout, stderr и traceback. После каждого неудачного запуска в системный промпт до конца задачи добавляется короткий вывод: что запускалось и какая строка ошибки. Предел — `code.max_iterations` неудачных запусков (по умолчанию 5), для H13 — 1.

**Конвейеры (Agentless).** Типовые задачи сначала проходят фиксированный конвейер, без свободного цикла:

- метрики из ноутбуков в CSV — из каталога Э6, где каждое значение сверено с ячейкой;
- график по логу обучения;
- исправление по traceback: запустить, найти место, показать окно кода.

Выбирает конвейер модель. Выбор проверяется по формулировке задачи: график — только если в задаче есть слово о графике; метрики из каталога — только если речь о ноутбуках или экспериментах и не назван лог или другой файл-источник.

## Набор задач

15 задач по демо-корпусу, у каждой есть скрытая проверка — pytest-файл, который агент не видит:

- исправления по traceback: деление на ноль, `NameError` в ноутбуке, отступ, ошибка разбиения данных;
- новые функции и скрипты: precision@k, размеры выборок, дозапись результатов в журнал;
- тесты к модулю;
- графики и таблицы: метрики из ноутбуков, эпохи из лога, столбчатая диаграмма;
- ускорение шага обучения.

Ошибки внесены патчами к копии корпуса. Набор проверен в песочнице ([`validate_tasks`](../src/rag_agent/evaluation/code_eval.py)): каждая проверка падает на стартовом состоянии задачи, а проверка задачи с внесённой ошибкой проходит на исходном корпусе.

Решённой считается задача, скрытая проверка которой прошла в песочнице после работы агента. Испорченный файл — изменённый `.py` или `.ipynb`, который после работы агента не разбирается.

**H13 подтверждена.** Цикл исправления решает 13 задач из 15, одна попытка — 9. Во втором прогоне интервал разницы не содержит ноль. В первом прогоне граница интервала касается нуля, но только потому, что c13 закончилась исключением обвязки. Задачи, которые решает только цикл: c05 (`NameError` в ноутбуке), c07 (traceback в переборе гиперпараметров), c09 (тесты к модулю), c13 (логика разбиения). Во всех четырёх первая попытка падает, а следующая исправляет ошибку по traceback. Цена цикла — задержка: p95 47 с против 17 с. Это в пределах NFR10 (5 минут на код-задачу с тестами).

**H14 на этом наборе не подтверждена и не опровергнута.** Перезапись файлов целиком решила столько же задач, что и ACI. Испорченный файл появился один раз за два прогона: в первом прогоне при перезаписи, на задаче c08, где агент исчерпал лимит шагов. ACI не испортил ни одного файла из 44 изменённых, перезапись — 1 из 42. Для вывода этого мало.

Причина, скорее всего, в размере файлов: модули демо-корпуса — от 24 до 270 строк, большинство меньше 130. Модель переписывает такой файл целиком без потерь. Преимущество ACI в SWE-agent проявлялось на больших файлах репозиториев SWE-bench, где при перезаписи теряются куски кода. Сколько правок отклонила проверка синтаксиса ACI, прогон не считает. Это стоит добавить в метрики, чтобы видеть, от скольких поломок она уберегла.

Базовый вариант «правка через оболочку (`sed`)» из формулировки ТЗ не реализован. Сравнение сделано только с перезаписью.

**Конвейеры.** c03 (метрики из ноутбуков) и c04 (график по логу) решаются за 2 секунды без свободного цикла во всех конфигурациях.

## Разбор неудач

- **c10 «эпохи из лога в CSV»** не решена ни в одном прогоне, и оба раза причина — выбор конвейера, а не модель:
  - в первом прогоне модель выбрала конвейер графиков, и шаблон нарисовал PNG вместо CSV. Проверка по словам о графике добавлена в 73da4e9;
  - во втором прогоне выбран конвейер «метрики из ноутбуков». Шаблон записал каталог ноутбуков в свой файл, а не эпохи из лога в `reports/epochs.csv`.

  Исправлено в fc3769d: этот конвейер выбирается только для задач о ноутбуках, в которых не назван лог, а таблица пишется по пути, названному в задаче. Перепроверка поставлена в очередь после обучения детектора.
- **c12 «скрипт размеров выборок»** решена только перезаписью. С ACI агент написал скрипт и сообщил об успешном запуске. Скрытая проверка запускает его как `python scripts/dataset_sizes.py`. Скрипт не добавляет корень проекта в путь импорта, как это делает `scripts/train.py`, и падает на `import ml_toolkit`. Агент проверял результат не тем способом запуска, каким его будет запускать пользователь.
- **Ложное «готово».** Во втором прогоне агент закончил со статусом «готово», а проверка не прошла:
  - 2 задачи из 15 в цикле с ACI: c10 (конвейер) и c12;
  - 2 задачи при перезаписи: c07 и c10.

  Отчёт агента не заменяет тесты. Поэтому diff и результат запусков показываются пользователю до переноса изменений.

## Ограничения

- **Выборка мала.** 15 задач дают интервалы шириной около 0.5. Задачи написаны автором на демо-корпусе, модули в нём небольшие. Тот же прогон на SWE-bench Lite был бы строже, но требует другой модели и нескольких суток вычислений.
- **Один прогон на конфигурацию.** Выводы генератора детерминированы только при одинаковом контексте. Два прогона цикла с ACI различаются решённостью одной задачи (c13) из-за исправления обвязки. Число неудачных запусков при этом различается и на решённых задачах: c06 — 3 против 1, c09 и c14 — 2 против 1.
- **Проверка синтаксиса** есть только для `.py` и `.ipynb`. Сломанный YAML или CSV она не заметит.
