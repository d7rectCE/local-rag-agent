# Э6. Каталог экспериментов и SQL

Критерий приёмки (ТЗ ч.1): реляционный каталог экспериментов, text-to-SQL, проверена H5.

- **H5:** SQL-инструмент решает агрегатные вопросы Q3 («лучший», «сколько», «все», «среднее» по многим ноутбукам), которые поиск по фрагментам не покрывает.

Набор — вопросы Q3 из [`evalsets/demo_v5.yaml`](../evalsets/demo_v5.yaml): 19 вопросов, из них 9 новых по многим ноутбукам сразу. У 16 вопросов есть эталонный SQL: по нему считается точность исполнения (EX). Генератор — `qwen3.5:9b`, судья — `qwen3.6:27b`. Спецификация — [`configs/ablations/e6.yaml`](../configs/ablations/e6.yaml), таблицы — [`reports/e6/`](e6).

## Что сделано

**Каталог (S2, S6).** При индексации парсеры заполняют детерминированные таблицы: файлы, ноутбуки, ячейки с ошибками, функции, вызовы, связи. LLM-извлечение добавляет эксперименты. Один вызов со структурированным выводом на ноутбук возвращает эксперименты, метрики и гиперпараметры, у каждого значения — номер ячейки, откуда оно взято.

Каждое значение сверяется с этой ячейкой:
- метрика должна быть напечатана в выводе или исходнике ячейки, с точностью до округления;
- гиперпараметр должен быть записан в её коде.

Не найденное ищется в других ячейках ноутбука, а иначе отбрасывается. Выдуманное моделью число в каталог не попадает. Округлять напечатанное модели разрешено не грубее 4 знаков: 0.9778 для напечатанного 0.97777 принимается, 0.99 для 0.9925 — нет. Названия метрик и выборок нормализуются (ROC-AUC → `roc_auc`, validation → `val`), чтобы фильтры в SQL были простыми.

На демо-корпусе: 8 ноутбуков, 12 экспериментов, 55 значений метрик, 30 гиперпараметров.

**Аналитическая база.** Отдельный файл `analytics.sqlite` пересобирается целиком после каждой индексации и атомарно подменяется, так что читатель никогда не видит полузаписанную базу. SQL-инструмент открывает его только на чтение, внутренние таблицы индекса (тексты фрагментов, служебные) ему не видны.

**SQL-инструмент в духе CHESS.**

1. Схема сужается до таблиц, ближайших к вопросу по эмбеддингам описаний таблиц и столбцов, плюс таблиц, через которые они соединяются.
2. Значения категориальных столбцов (датасеты, модели, названия метрик), похожие на слова вопроса, передаются подсказками, чтобы фильтр использовал сохранённое написание.
3. Из встроенной расширяемой базы добавляется несколько похожих примеров «вопрос → SQL».
4. Модель пишет один SELECT. Он проверяется sqlglot (если установлен), принудительно ограничивается LIMIT и выполняется на соединении только для чтения: авторизатор SQLite разрешает только чтение, есть таймаут.
5. При ошибке или пустом результате модель получает обратную связь и пробует снова, не больше `catalog.attempts` раз (3).

**Где вызывается.**
- **Прямой путь:** маршрутизатор отмечает агрегатный вопрос, SQL выполняется до генерации, результат идёт первым источником.
- **Агент (Э7):** `sql_query` — один из инструментов. После первого прогона H5 агент для агрегатного вопроса начинает с запроса к каталогу автоматически (шаг 0, 73da4e9). Свободный агент выбирал SQL только для 37% вопросов Q3.

**EX.** Точность исполнения сравнивает результат запроса модели с результатом эталонного SQL на том же каталоге:
- строгая — строк столько же, и каждая эталонная строка содержится в какой-то строке модели. Лишние столбцы допускаются: система добавляет путь и ячейку для цитирования. Числа сравниваются до 4 знаков;
- по значениям (73da4e9) — в строках с числами должны совпасть только числа, а идентифицирующая строка может быть другой. Например, название эксперимента вместо пути к ноутбуку. Строгая метрика считает такой ответ ошибкой, хотя пользователю он не хуже.

## Результаты

Три конфигурации на 19 вопросах Q3. Основной — второй прогон ([`reports/e6/ablation.md`](e6/ablation.md)): в нём агент начинает агрегатный вопрос с SQL, и судья видит фрагменты целиком. Первый прогон, со свободным агентом, — [`ablation_run1.md`](e6/ablation_run1.md). Δ — парный бутстреп по вопросам относительно агента с SQL.

| Конфигурация | Точность Q3 (судья) | Δ [95% CI] | SQL на Q3 | Ложные отказы | Верность контексту | EX (n=16) | p95, с |
|---|---|---|---|---|---|---|---|
| **агент с SQL-инструментом** | **0.763** | — | 89% | 1 | 0.84 | 0.31 | 20.7 |
| H5: без SQL, только поиск | 0.421 | **−0.342 [−0.61; −0.08]** | 0% | 8 | 0.95 | — | 17.0 |
| без агента: SQL перед ответом | 0.816 | +0.053 [−0.11; +0.26] | 89% | 2 | 0.95 | 0.31 | 14.4 |
| *первый прогон:* свободный агент с SQL | 0.526 | — | 37% | 5 | 0.90 | 0.00 | 19.6 |
| *первый прогон:* SQL перед ответом | 0.816 | +0.289 [+0.11; +0.50] | 89% | 2 | 0.95 | 0.31 | 14.9 |

**H5 подтверждена.** С SQL-инструментом агрегатные вопросы решаются вдвое чаще: 0.76–0.82 против 0.42. Интервал разницы не содержит ноль. Без каталога агент по фрагментам 8 раз из 19 отвечает «в архиве этого нет». Вопросы вида «сколько ноутбуков на breast_cancer», «какие модели пробовали на digits», «лучшая accuracy на тесте по всем ноутбукам» требуют собрать факты из многих файлов, а поиск возвращает пять фрагментов.

**Где SQL решает, а поиск нет** (судья, агент с SQL против без SQL):

| Вопрос | С SQL | Без SQL |
|---|---|---|
| a-01 максимальная accuracy на валидации по всем ноутбукам | 1 | 0 |
| a-02 какие модели пробовали на digits | 1 | 0 |
| a-04 максимальная accuracy на тесте | 1 | 0 |
| a-06 какие ячейки ноутбуков упали с ошибкой | 1 | 0 |
| q3-01, q3-02 ROC-AUC и число ноутбуков на breast_cancer | 1 | 0 |

**Свободный агент выбирал SQL редко.** В первом прогоне агент сам решал, звать ли `sql_query`, и выбрал его для 37% вопросов Q3: точность 0.53 против 0.82 у фиксированного «сначала SQL». Это аргумент Agentless: для типового вопроса фиксированный шаг надёжнее свободного выбора. После исправления агент для агрегатного вопроса (по оценке маршрутизатора) начинает с запроса к каталогу. Доля SQL выросла до 89%, точность — до 0.76, и разница с прямым путём (+0.05) больше не значима.

Прямой путь остаётся чуть точнее и быстрее (p95 14 с против 21 с). У агента ниже верность контексту (0.84 против 0.95): в ответ попадают выводы, сделанные по промежуточным шагам, которых нет в итоговых источниках.

**EX (0.31) заметно ниже точности ответов (0.76–0.82).** Запрос модели часто верен по смыслу, но возвращает строки другой формы. Для вопросов о переборе learning rate или alpha модель соединяет метрики с таблицей гиперпараметров, а эталон берёт вариант из `metrics.variant`. Число строк от этого другое, и EX не засчитывает запрос, хотя генератор выбирает из результата верные значения. EX по значениям здесь не помогает: он ослабляет сравнение строковых столбцов, а не числа строк. EX полезен как диагностика SQL-инструмента, но не как мера ответа пользователю.

**Где SQL ошибается** (0 у агента с SQL):

- **a-07 «какие функции ml_toolkit чаще вызываются в ноутбуках».** Модель отфильтровала `functions.name LIKE 'ml_toolkit%'`, но модуль записан в столбце пути, а не в имени функции. Запрос вернул пусто, и ответ — «статистики нет». Ошибаются все три конфигурации.
- **a-05 «средний ROC-AUC по перебору learning rate».** Агент сгруппировал по ноутбуку и варианту и получил пять значений вместо одного среднего. Затем модель посчитала среднее сама и ошиблась в сумме: 4.9374 вместо 4.9574. Прямой путь посчитал `AVG` в SQL и ответил верно. Арифметику стоит оставлять базе, а не модели.
- **q3-07 «какое расписание learning rate дало лучшую accuracy».** Запрос соединил метрики с гиперпараметрами и обрезал до одной строки, названия расписаний в результат не попали. Модель прочитала таблицу во фрагменте неверно: «cosine и constant по 0.9639», хотя у cosine 0.9583.
- **d-q3-01 «модель с наибольшим ROC-AUC в таблице мартовского отчёта».** Вопрос о таблице в DOCX, а каталог собран из ноутбуков, так что SQL здесь бесполезен. Ответ по фрагменту отчёта перепутал 0.998 и 0.9998. Ошибаются все конфигурации.

## Ограничения

- **19 вопросов Q3,** написанных автором на демо-корпусе: 8 ноутбуков, 12 экспериментов. Каталог приватного корпуса будет больше и грязнее, и качество извлечения нужно проверить на нём: доля отброшенных сверкой значений, полнота по ноутбукам.
- **Примеры «вопрос → SQL» и описания таблиц** писались под этот каталог. Отложенной выборки для них нет.
- **SQL-инструмент не видит данные загрузок** (Э13). Агрегатные вопросы по загруженной таблице (u-l-06 в отчёте Э13) пока не решаются. Естественное расширение — временная SQLite для табличных загрузок.
